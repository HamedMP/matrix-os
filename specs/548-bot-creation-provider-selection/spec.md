# Bot creation and current provider choices

Tracking: [ENG-204](https://linear.app/matrix-os/issue/ENG-204/fixbots-repair-automatic-creation-and-subscription-model-setup). Requester approved the final plan on 2026-10-09. Recommend affected product/provider owners review the managed custom-Bot creation journey and authorization boundary; this recommendation is not an additional implementation gate.

## Goal and journey

Recipe setup must accept the Automatic choice it offers. New agent setup must let an owner explicitly choose a connected ChatGPT subscription and a current supported GPT model for a new managed Bot. Model refresh must preserve all unsaved fields and the explicit funding choice. Saving creates the definition/conversation; it does not run inference or perform integration actions.

An explicit subscription selection creates a managed Bot through server-owned creation provenance and the qualified coordinator runtime. It must not enable ordinary subscription routes on legacy custom definitions. Existing custom Bots retain their saved executor, Full access consent, history and grants. Automatic may use only existing eligible Matrix funding/owner API sources and must never borrow a subscription implicitly.

## Required behavior

1. Validate the exact Automatic contract at the actual startup creation seam, including rejection of extra options and malformed model/source pairs. Keep runtime/source qualification at execution; creation cannot mint funding authority.
2. Reuse durable, owner-scoped Bot creation operations for new managed custom Bots. Custom instructions and selected recipe skills are data, not grant authority. The server resolves and persists a bounded coordinator recipe and exact model/account/grant selection. Client-provided recipe references or route strings cannot supply server provenance. Idempotent retries reuse the created Bot; later open/configuration failures preserve it with safe recovery feedback. Removing a recipe from a retained new-editor draft must explicitly clear the committed recipe on that same Bot, including recovery retries.
3. Select Connection then Model from one canonical catalog derivation. Expose explicit Refresh models; refresh on opening setup/editor and returning from provider setup. Catalog discovery and forced refresh in Web and Electron use the shared funded-readiness renderer deadline (`FUNDED_AI_READINESS_TIMEOUTS.rendererRequestMs`), including cold-start readiness; other Agent requests retain their existing timeout. In the recipe chooser, discovery replaces the Plus icon inside the existing Start from scratch card with the shared reduced-motion-aware spinner and an accessible loading status; do not add a separate status row or change the chooser/card geometry. Keep the card title and description in place. A failed load exposes safe recovery text inside that same card and makes its single native button a keyboard-focusable Retry models action, without opening the editor or nesting another button. Retry restores the in-card spinner and remains blocked by saving, capability and capacity conditions. Outside the chooser, retain compact loading/error feedback beside the library/editor controls. Do not offer retry before failure or while pending. All retries coalesce through the existing owner/client scope and use shared semantic theme tokens. Catalog refresh changes choices, not draft name/description/instructions/recipe, explicit selection or stable create request identity. Failed refresh drops stale executable choices; only a successful current-scope response restores them. Revoked selections remain visibly unavailable and cannot be saved/dispatched. No fallback to another funding source and no periodic discovery loop.
4. Run the new managed Bot only in its owned dedicated conversation, through the existing sandbox/broker and live exact owner/model/grant/revision admission. Revalidate queued/retried work and every upstream send. A foreign/archived Bot, stale grant, forged recipe provenance or ordinary-only subscription source fails closed.
5. A managed custom definition must be executable before it is persisted. Reject unsupported Hermes-only skills for these Bots at create/edit boundaries while preserving legacy Hermes recipes. Validate the entire composed system prompt (name, instructions, server-resolved skills, selected integration account intent and runtime framing) against the same runtime budget before creation reservation/definition/Chat or an edit write. Rejections retain the previous definition/revision and create no new operation or Chat; the editor must not offer unsupported skills or silently rewrite a draft. Description-only edits and archive-only withdrawal compare supplied executable fields against the saved values, so unchanged supported full editor payloads do not require installed-skill discovery. Real executable changes and reactivation still validate. Retained incompatible recipes remain blocked from Save until removed; the separate Archive action uses a minimal withdrawal payload and remains available. If installed skill content later exceeds the prompt budget, runtime composition must reach the existing task-aware guard and persist a blocked task with `policy_denied`, without starting inference. Selected integration account labels remain in the shared executable job as owner intent, while current grants and exact-action approvals remain the permission source.

## Security and wiring

Existing gateway authentication remains personal-principal based; owner IDs never come from client bodies. Existing Agent POST/PATCH ordinary-subscription rejection stays intact. New managed creation uses an authenticated mutating Bot action with streaming body limit and strict bounded schema; `POST /api/chat-agents/managed-custom` creates the definition through the durable instantiation service. Canonical catalog refresh is an authenticated GET using the existing bounded transport. No public route, credential import, secret-bearing DTO, direct worker networking or sandbox relaxation is introduced.

| Operation | Authentication | Boundary |
| --- | --- | --- |
| Canonical provider catalog read/refresh | Existing gateway principal | Owner/runtime catalog and current grant projection |
| Recipe Bot instantiation | Existing gateway personal principal | Exact Automatic or qualified explicit coordinator selection |
| New managed custom-Bot creation (`POST /api/chat-agents/managed-custom`) | Existing gateway personal principal | Strict bounded input, server provenance, owner-scoped idempotency |
| Legacy Agent create/PATCH | Existing gateway personal principal | Retained applicable route/permission and revision checks |
| Dedicated Bot Chat turn | Existing gateway principal plus owned active binding | Current exact definition, execution generation and account/grant/model |

Startup registers shared selection validation and managed creation dependencies before advertising availability. UI submits user-authored fields plus explicit supported selection; service validates before reservation/writes. Related canonical Chat/binding/outbox writes are transactional, use current owner serialization and never adopt unrelated occupied deterministic IDs. Managed custom operations use a server-reserved request namespace, rejected by generic recipe creation. Runtime qualification requires that database provenance, the matching definition creation hash and live owner-scoped direct Chat; an editable recipe reference cannot convert an ordinary operation into a managed custom Bot. Durable creation states preserve failed file/open recovery; retries cannot duplicate definitions or silently change grants.

Catalog orchestration coalesces bounded requests and rejects stale out-of-order or wrong-runtime completion. Errors retain draft and safe state; unknown/provider/path/database messages are not shown. Existing request/body/count/native deadlines and shutdown drains remain in effect. New temporary/buffered data requires bounded size and cleanup; no unbounded request registry or recurring polling timer.

## Funded scratch creation and explicit recovery (ENG-371)

This repair extends the existing managed custom creation path to the exact funded `matrix_pi_default` selection with no additional options. A funded scratch Bot must receive the same server-reserved creation provenance and dedicated Chat as a qualified subscription Bot. Generic Agent persistence followed by a Bot Chat binding is insufficient: ordinary Matrix AI admission intentionally refuses Bot-bound Chats. Retain that boundary. Source readiness and the complete executable prompt must be validated before reserving a creation or writing a definition.

Recipe is optional. Once added, its expected output is required and must be visibly identified as such. The current draft's validation determines both submission eligibility and actionable feedback beside Create. Missing name, instructions, model or recipe requirements must not result in unexplained disabled controls. Removing or changing a recipe recomputes the current conditions. Catalog failures offer retry without discarding the draft or replacing its funding source.

Before a create request, retain its exact payload and owner-scoped request identity. An unknown transport outcome is not proof that no Bot exists. Retry the same operation and recover the exact returned identity before applying later draft edits; never adopt an entry by name. A synchronous in-flight guard prevents multiple submissions before the loading state renders. Successful new creation opens the returned dedicated Chat. Readback or open failures retain the committed Bot and editable draft for recovery.

An explicit recovery action may convert an existing unsupported funded generic definition without replacing its Bot or Chat. The authenticated principal supplies ownership; the request supplies only a bounded base revision. Require an active personal direct binding, an unchanged funded definition, no archived/removed/shared state, no active or queued work, no immutable ordinary provider binding, and only Agent-context historical runs. Histories outside those conditions fail with an actionable conflict rather than a provider-lock rewrite.

Slow source and definition discovery runs outside the owner/Chat locks before reservation. Locked snapshot and revision/hash checks reject intervening edits, while an already active recovery replays without depending on provider discovery. Recovery reserves a separate server-owned managed operation using the existing Bot/Chat IDs and the exact original server-read creation hash. Definition promotion uses the existing owner lock and revision/hash comparison, preserves executable fields and creation hash, and adds managed provenance. Activation rechecks the live definition, source and owned binding; related database writes and notification events commit together. File/database interruption leaves the same operation recoverable through explicit retry. Ordinary instantiation reconciliation must not activate an unpromoted recovery operation. Explicit recovery readback opens the exact recovered identity without applying stale editor fields over concurrent definition edits. Keep all messages, turns, runs, grants and approval records attached to their existing identities. Account labels, migration and recipe provenance never grant access.

| Recovery operation | Authentication | Boundary |
| --- | --- | --- |
| `POST /api/chat-agents/:agentId/recover-managed-custom` | Existing personal gateway principal | Strict revision/body/path validation; exact owned active legacy Bot/Chat; qualified funded source; identity-preserving, idempotent activation |

Required evidence includes funded and subscription creation compatibility, recipe field/retry/removal coverage, uncertain-response and repeated-submit recovery, failed recovery at each durable boundary, concurrent/conflicting/foreign-owner rejection, preserved history/grants, and real Electron Desktop creation and replies with and without a recipe. Applying recovery to the existing owner Bot was subsequently cancelled by the requester; actual legacy recovery UI/apply remains unverified and is excluded from this acceptance run. Recovery still requires automated interruption/reopen and history/grant invariants before shipping. Record client source and actual backend version independently. ### Retry and interrupted-recovery contracts

1. **Scope / trigger:** A create response can be lost after persistence; recovery can promote the owner file before its database activation commits. Closing the editor must not discard durable operation identity.
2. **Signatures:** `GET /api/chat-agents?includeManagedCustomRecoveries=true` opts into optional `managedCustomRecoveries: { agentId, baseRevision }[]`. Explicit recovery remains `POST /api/chat-agents/:agentId/recover-managed-custom` with strict `{ baseRevision }`.
3. **Contracts:** The default list response retains its old strict shape for installed clients; the query accepts only an optional literal `true`, rejecting other/unknown values. Projection items are strict, capped at100, and use a positive safe-integer original revision. Derive them from the authenticated owner's exact unfinished reserved operation selected by expected request ID, matching definition hash/snapshot and owned idle direct Chat. The projection is read-only response data, never editable definition authority. Listing must not probe providers or create workspaces/operations. No new environment or schema migration is required.
4. **Validation / error matrix:** A fresh definitive pre-write validation/auth rejection may release the initial request. Once a transport/conflict/capacity/server failure makes persistence uncertain, later400/auth failures cannot erase the retained payload/request ID. Unknown failures stay generic. Active, foreign, mismatched-hash or ineligible operations are omitted from unfinished recovery projection; database failures fail the read rather than masquerading as absence. Final POST rechecks all authority and concurrency conditions.
5. **Good / base / bad cases:** Good:503→400→edit replays the original create and edits only its verified identity. Base: first fresh400 lets the user correct an invalid draft. Bad: assigning a new ID after the uncertain operation or inferring recovery authority from a file recipe reference. A promoted revisionN+1 reopens with the server-projected baseRevisionN; an active operation no longer projects unfinished recovery.
6. **Required tests:** Assert exact request ID/payload retention across uncertain→400 responses; A→B→A edits after two open failures save against the latest saved revision. Assert promoted-file rollback→list→reopen keeps Recover Bot and submits the original revision, even after provider availability changes. While this unfinished operation is projected, Save is disabled and submit is guarded with explicit finish-recovery guidance; edited drafts must be undone or reopened before Recover. Cover active, foreign owner, stale hash, stale operation namespaces and concurrent mutation exclusions; preserve history/grants and explicit POST validation.
7. **Wrong vs correct:** Wrong: `status === 400` always clears the attempt, or `recipeRef` always hides recovery. Correct: latch uncertainty until an exact committed identity is verified, compare edits against the latest saved Agent, and use authenticated unfinished-operation projection for reopening recovery.
