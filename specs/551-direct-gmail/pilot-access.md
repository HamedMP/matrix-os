# Isolated pilot access (ENG-355)

The pilot reuses existing Clerk identities. It does not create another Clerk instance or grant Google access. This app-wide boundary is independent of native Gmail eligibility, Google processing profiles/consent, and the stricter Google-data host controls.

## Operator configuration

- `MATRIX_PILOT_ACCESS_ENABLED`: absent or exact `false` preserves ordinary behavior; exact `true` enables the gate. Other values are invalid.
- `MATRIX_PILOT_ALLOWED_CLERK_IDS`: when enabled, a required comma-separated list of at most 100 Clerk user IDs, each at most 128 characters (`user_` plus ASCII letters/digits). Outer whitespace is trimmed; empty/malformed entries or input over 12,999 characters invalidate configuration. IDs are private deployment configuration, never email addresses or client assertions.
- The shared contracts loader returns an immutable `disabled`, `enabled`, or `invalid` snapshot. Invalid platform configuration, or an enabled platform without a Clerk verifier, refuses application construction. The shell refuses private requests with a generic 503 when invalid.

The platform still needs its existing supported Clerk server-verification configuration. No public-key-only startup switch or limited-authority Clerk secret mode is introduced. Assigning production Clerk server authority, configuring the existing Clerk instance's domains/redirects, and changing service ingress/IAM require separate operator review. This change performs none of those actions. Membership changes require replacement configuration/restart; previously issued Matrix tokens are checked against the new cohort on subsequent requests.

## Authentication matrix

| Owner HTTP APIs, app-session exchange/provisioning, billing, integration management, account management | Host-independent early checks of cryptographically verified Clerk and Matrix sync-JWT actors; exact cohort membership plus all existing route guards. The consuming Clerk verifier checks membership again so a transient earlier verification failure cannot become approval on retry. |
| Browser shell and native Matrix sessions | Signed Clerk identity or Matrix session principal must be a member. `x-platform-user-id`, route cookies, email, and request body fields never prove membership. Signed platform shell forwarding additionally requires the existing runtime bearer plus HMAC actor proof. |
| `POST /auth/device/approve` | Verified cohort Clerk actor plus existing CSRF/code checks. |
| `POST /api/auth/device/code`, `POST /api/auth/device/token` | Existing bounded device-code capability protocol remains public. Token issuance independently checks the stored approved Clerk actor before minting; removed/nonmember approvals cannot obtain a token. |
| Owner WebSocket upgrade, including `/vm/:handle/ws...`, code host, and query-token paths | Existing signature/runtime access checks, then exact resolved actor membership before opening the upstream. Rejections are bodyless HTTP statuses with `Cache-Control: no-store`. Internal collaboration-control and Gemini service upgrades retain their independent machine authentication. |
| `GET /api/integrations/gmail/oauth/callback` | Exact method/path exception only. Existing one-use stored OAuth state binds the original owner; a browser session is not substituted. |
| `POST /api/integrations/gmail/pipedream/callback` | Exact method/path exception only. Existing attempt secret/provider verification remains mandatory. |
| `POST /api/integrations/webhook/connected` | Exact provider-signature callback remains independently authenticated. No webhook-prefix cohort bypass. |
| Native Mobile `/apps/:slug/*` | Initial GET/HEAD one-use `session` capability and subsequent per-slug HMAC cookie are verified by the actual gateway. Platform routes only to a DB-owned cohort runtime, forwards the original capability, and injects **no** platform bearer or actor proof. A route cookie alone is insufficient. App-cookie requests retain their existing app-scoped methods; no general owner API is exposed. |
| Explicit VM signed app-asset / native stream capabilities | Existing exact capability validators remain authoritative; anonymous capability targets must belong to a cohort owner. No inferred actor proof is minted. |

| `GET /health`, sign-in/static prerequisites, existing public metadata | Health and exact capability dispatch remain available; the shell preserves only its explicit sign-in/static prerequisites. Public metadata never authenticates an owner. |

Nonmember responses are generic and uncached. Protocol exceptions do not authorize arbitrary callback suffixes or methods. Ordinary disabled behavior is preserved.

## Native Mobile wiring and regression

`apps/mobile/lib/storage.ts` resolves a hosted selected computer's launch URL to canonical `/apps/...`; `AppRuntimeFrame` does not supply a Clerk header. The authenticated app-session mint API remains cohort protected. Production host nginx (`scripts/install-server.sh`) routes `/apps/` directly to gateway port 4000, not Next.js, so no shell cohort exception is needed. The gateway consumes the one-use token and issues/verifies the per-slug cookie. Avoiding platform bearer injection is essential: its app-asset shortcut must not bypass that cookie verifier.

The composed regression uses real platform routing, gateway auth, app-runtime registrar, one-use store, HMAC cookie middleware and static dispatcher. It checks native mint/launch, replay, forged asset cookie, unsigned route-only cookie, no fabricated platform actor, and noncohort target refusal before upstream dispatch. Other focused tests use genuinely signed Clerk/Matrix/MCP tokens, HTTP/session/native issuance and WebSocket denial, permitted actors, default-disabled behavior and malformed configuration. These are source tests, not evidence of deployed sign-in or five-surface qualification.

## Native Mobile build target and local state

Native Mobile selects its hosted service from the literal Expo build-time public setting `EXPO_PUBLIC_MATRIX_HOSTED_ORIGIN`. Absent configuration preserves `https://app.matrix-os.com`. The only other supported value is exact `https://gmail-pilot.matrix-os.com`; malformed values, paths, query strings, userinfo, ports and other hosts fail initialization instead of falling back to production. This is immutable JS-bundle configuration, never a user-entered URL, persisted preference or server response. The existing production Clerk instance's public `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` supplies the client identity; it does not grant platform access or replace the server cohort check.

The same origin controls computer discovery, canonical journey requests, routed HTTP, WebSocket token issuance/URLs, app-session launch URLs and the exact `/auth/gmail?state=...` launcher allowlist. Pipedream's existing trusted connect URLs remain supported. An inactive built-in Matrix origin cannot be restored as a custom gateway or selected for Basic Auth. Ordinary custom gateways do not acquire hosted classification.

Production's persisted keys stay unchanged. Pilot gateway selection, query snapshots and remembered journey readiness use separate `.gmail-pilot` keys; restoring or signing out of the pilot does not read, overwrite or delete those production entries, even for the same Clerk user. These namespaces do not isolate every app artifact: Clerk SDK sessions, preferences, push/analytics state and older offline/collaboration stores remain app-sandbox scoped. Use a separate pilot binary with distinct iOS bundle identifier and Android package, a separate update channel, and an isolated compatible runtime/build configuration. Do not load a pilot bundle into the primary installed app or promote it through the existing preview-to-production channel flow. No installation or existing device data was changed by this source unit.

### Separate native binary and exact callbacks

`app.config.js` extends the production `app.json`. The same public hosted-origin setting selects the pilot name **Matrix OS Gmail Pilot**, iOS bundle identifier and Android package `com.matrixos.mobile.gmailpilot`, and the unique `matrixos-gmail-pilot` scheme. The production app keeps `com.matrixos.mobile` and `matrixos`. Native inputs now require a fresh `0.2.8` binary: the existing OTA/native fingerprint guard remains unchanged, and installed `0.2.7` primary apps do not receive `0.2.8` OTA updates. All other production native configuration remains unchanged. The `gmail-pilot-device` EAS profile is an internal physical-device development client, with a separate `gmail-pilot` channel, a distinct `gmail-pilot-0.2.8` runtime version and `updates.enabled=false`; it must never enter the preview-to-production promotion flow. Pilot configuration also disables the dev client's generated `exp+<slug>` scheme, which would otherwise collide with the primary app. Start Metro for this target and open the pilot's explicit scheme, rather than the shared generated launcher scheme. Development-client Metro loading is separate from EAS OTA updates.

Native Clerk SSO uses exact `matrixos-gmail-pilot://sso-callback`; Connect Apps uses exact `matrixos-gmail-pilot://integrations`. A synchronous root `NativeBuildBoundary` checks before mounting Clerk, query, analytics or gateway descendants, including a cached signed-in session. It never clears an existing session or cache on denial. Before password, email-code, browser SSO, native Apple sign-in or an integration connection starts, the existing `expo-application` native module must report the selected target's exact application ID. A changed Expo manifest or Metro bundle cannot substitute for the installed binary's identity. Unknown IDs, opposite-target binaries and mismatched SSO redirect overrides fail before Clerk or integration requests. An existing email-code attempt rechecks the native target before code submission and again before activating the verified session; these checks do not repeat gateway-storage writes. Only explicit `Platform.OS === "web"` preserves the existing Expo Web subtree and browser-origin `makeRedirectUri` semantics (including its existing operator override); web has no installed native ID to attest. Unknown native platforms and missing native IDs fail closed. This protects accidental cross-target Metro use, not malicious JavaScript or a trusted server attestation. Production's default native callback addresses remain unchanged. The unique integration return is only a navigation signal; authenticated connection state and exact attempt receipts still establish completion.

The isolated integration broker must explicitly configure `MATRIX_NATIVE_MOBILE_TARGET=gmail-pilot`. Absent configuration defaults to `production`; every other value, including empty, fails closed. Both public and signed internal platform integration registrars receive that one startup-selected target, as does the native OAuth service. Direct gateway integration startup reads the same operator setting when it owns integration routes. No request header, body target selector, selected computer URL or arbitrary redirect allowlist can change this policy. The selected target accepts exactly its own integration URI (no extra slash, query, fragment or alternative scheme); omission retains browser completion. Native OAuth checks stored return policy before provider exchange and the HTTP callback independently checks lifecycle output before redirecting. Pipedream receipt and legacy token issuance use the same selected return for success and failure. The existing HTTPS `GMAIL_OAUTH_CALLBACK_URL`, one-use state/cookie, signed webhook/attempt proof and cohort requirements remain separate and unchanged.

The per-user host already routes centrally brokered integration traffic through its trusted `PLATFORM_INTERNAL_URL`; this unit does not add provider credentials or mobile redirect settings to every VPS host template. Configure the policy on the actual isolated broker, and explicitly on any directly hosting gateway. The large platform startup and generic integration entrypoints receive typed composition calls only; the next integration protocol should extract those registrar blocks before adding more behavior there.
