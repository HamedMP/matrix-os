# Qualified funded lease foundation (ENG-355)

This layer adds schemas and an explicit persistence helper. It installs no runtime routes, startup migration, lease manager, proxy enforcement, provider approval or account configuration. A child row is neither Google consent nor a live processing grant.

`google-qualified-funded.ts` defines the separate `matrix-google-qualified-funded-v1` discovery, issue and check protocol. Existing funded v1 shapes remain unchanged. Discovery/issue/check requests select only a supported API/canonical model; issue requires an explicit request class and expected descriptor digest, and check also requires the opaque credential. No request supplies an authoritative relay URL, owner, reviewed credential identity or approval. Authenticated server control resolution supplies those facts. The response binding carries the exact descriptor, canonical digest, authoritative relay base URL, API/model, request class and original review expiry. Its relay endpoint/API/model/expiry must agree with the descriptor; a lease token cannot outlive that review. Parsing proves shape and consistency, not evidence authenticity or SHA-256 correctness.

Qualified credentials use only `sk-matrix-google-funded-<tokenId>.<43-character-base64url-secret>`. Their strict schema/parser rejects the legacy `sk-matrix-funded-` prefix, malformed material and trailing whitespace; format parsing returns only the token ID and is not authentication. The qualified lease validator checks the exact embedded token ID, explicit request class and positive lifetime of at most sixty minutes. The token ID, private HMAC token hash, existing audience/scope and child foreign key remain compatible with the existing database design; the future issuer must hash the complete new opaque token.

This prefix is an explicit old-code compatibility boundary. Existing legacy issue-response, check-request and authorization-request schemas and the anchored `FUNDED_TOKEN_PATTERN` in the old platform reject the new prefix even when the old replica has no knowledge of the child table. Qualified requests likewise reject old tokens; no prefix translation, stripping, legacy retry or ordinary-token substitution is allowed. This protects that credential from acceptance through old legacy parsers; it does not install a qualified checker or prove every egress path is guarded. Existing legacy tokens/payloads/parsers remain unchanged. The separate qualified protocol must be implemented before any new token is minted or used, and new runtime/relay paths must still authenticate its full hash and validate the exact child/profile/consent at actual use.

`installAiFundedRouteBindingSchema` explicitly creates the additive `ai_runtime_credential_routes` child table, keyed by the existing credential foreign key with deletion cascade. It bounds descriptor JSONB to 64 KiB and constrains scalar consistency. Its caller must own the schema migration lifecycle; no existing core schema marker changes here. No content, raw credential, operator evidence text or owner consent is stored in the child.

`insertAiFundedRouteBinding` requires a real caller-owned Kysely transaction. It locks the existing credential, checks exact owner/machine/runtime identity, active machine ownership, token audience/scope/class/revocation/time and the complete original review window, then recomputes the domain-separated SHA-256 over the contracts canonical descriptor encoding. A longer-lived token is refused; its expiry and the descriptor are never rewritten. The issuer must clip token expiry before minting in a later unit. `ON CONFLICT DO NOTHING` permits exact retries; a different binding for the same token is refused. Caller rollback removes the child. The helper never creates a transaction or closes a shared pool.

Before the first locking statement, insertion tightens transaction-local PostgreSQL `statement_timeout` to at most 5 seconds and `lock_timeout` to at most 2 seconds, preserving any stricter nonzero caller value (`0` means unlimited). It reads `pg_settings` normalized integer millisecond values and verifies their unit/type instead of parsing user-facing unit strings. Limits revert when the caller transaction commits or rolls back. SQL timeout errors remain database failures for the future server's generic mapper; no retry or downgrade is inferred. These per-statement limits do not bound pool acquisition, the whole issuer transaction, standalone reads or schema installation. Their caller still needs an overall deadline and pool bounds; none is installed here. An HTTP timeout or `Promise.race` alone would not cancel a queued database lock query.

`readAiFundedRouteBinding` requires exact token/identity/API/model/class/digest expectations, validates current joined token and machine facts, recomputes the digest and returns the original binding. Only genuine absent child returns null; mismatches, stale review and revoked/expired tokens throw the fixed typed denial. Database failures propagate as failures rather than absence. Callers must map unexpected errors to generic external responses. Reads are snapshots, so callers still revalidate at dispatch/output release and use the existing account-deletion admission lock in their enclosing authorization transaction.

Next composition must authenticate runtime discovery/issue via actual handle/machine/runtime-token epoch, resolve only the fixed trusted proxy control URL, atomically mint token plus child, and distinguish qualified check/authorization from legacy. Legacy check/authorize must refuse route-bound tokens; qualified calls must refuse ordinary tokens. A separate bounded gateway cache must never fall back to legacy or substitute a new route after consent. Proxy actual dispatch and streaming release must compare the same binding against fresh config/review evidence, preserving billing receipt settlement even when output is discarded. Those behaviors are explicitly absent from this foundation.

Only the existing Workers descriptor is recognized. Anthropic implicit billing and future Bedrock require separate reviewed adapters. Operator account-state evidence, current Google processing profiles/consent, deployment configuration, hosted verification and public documentation in the private site repository remain separate stack deliverables.
