# Completion and assistant attachment message copies — ENG-355

`finishRun` and `appendAssistantAttachment` are extracted from the oversized run lifecycle repository into focused helpers before optional message-copy composition. Uninstalled behavior remains unchanged. The existing private `assistantDeltaWrites` hook now also supports `writeRun({owner,chatId,runId,outputMessageId?},transact,content,signal?)`; attachment-reference writes reuse its single-message method. Cancellation remains a separate optional argument. Inputs and validated output/attachment metadata are snapshotted before waits.

Run completion acquires the owner context/birth fence, then provenance global lock 551035503. An unlocked, bounded query discovers at most 64 assistant message IDs in the run; an explicit completion output ID is included. Registry rows are locked in sorted entity-reference order before chat, run, message and encrypted-sidecar rows. After chat/run locks, the existing-ID set must still match the observed set: an unqualified concurrent writer cannot introduce a row that silently escapes registration. All existing hashes/origins/revisions must match. Completion then updates messages/run/turn/preview in the same transaction and re-registers every changed canonical message. Missing legacy lineage, modified payloads, expired/closed contexts, stale candidates or capacity overflow fail closed without partial completion.

The canonical hash export and exact persisted JSONB projection are unchanged. Streamed text, snapshot recovery, completion replacement/output insertion and attachment references in message parts all use the same owned-message hash. Effective retention is the strict minimum of originating source/context deadlines and every existing affected copy deadline, preserving all mixed origins. No new owner retention choice is invented. Source expiry and cancellation are checked through the final write and again after actual outer COMMIT by the shared whole-batch release ledger. Committed content can exist while its acknowledgement/live batch is withheld; retry requires renewed admission rather than assuming rollback.

These hooks do not authorize an AI provider. The attachment-reference message is covered, but `chat_attachments` metadata and referenced file bytes still require independent lineage/deletion handling. Activity events/transitions/eviction, run/queue context snapshots, persistent full outbox projections and their redactors remain installation blockers. The parent stack separately owns canonical-message redaction; this unit supplies no deletion handler or all-copies completion claim. No hook is installed at startup here.

Synthetic native PostgreSQL tests cover multiple finalized messages, supplied output insertion, changed/missing lineage, mixed-origin retention, rollback, owner/cancellation checks, immutable input, actual COMMIT withholding, candidate caps/change detection, and competition with a real purge worker holding a later registry copy. Original delta and ordinary repository tests preserve existing behavior. No customer data, network or provider calls are involved.
