# Pilot outbox content boundary — ENG-355

Private server composition can construct `ChatRepository(..., {contentProjectionMode:'metadata-only', ...})` using the existing fourth options argument. The default remains the existing content projection behavior. The constructor snapshots the options, and nested repositories retain the setting. No route, request payload, environment switch or client setting is added here. The controlled startup must install this boundary before creating/classifying new pilot chats; this unit does not install it.

In metadata-only mode, canonical event writes retain owner/chat/cursor/revision/event-type/timestamp scalar fields with an empty payload. `appendOutbox` skips content capture and failure-telemetry projection entirely. Message bodies/deltas, previews, activity summaries, error text and arbitrary metadata are not copied into the personal outbox. Shared queued-run routing retains its existing scope/sequence semantics while persisting an empty collaboration-event payload. Externally committed events are also copied to scalar notification fields without accessing their payload. No context or provenance lookup is introduced after content locks; no additional pool, timer, cache or registry is created.

Existing content-negotiating clients receive the established `chat.event` invalidation frame and refresh through current owner reads. Owner detail/preview/export inspection remains available under existing authorization; this option does not certify model-history assembly or authorize any AI provider. Canonical message, activity and context persistence remain separate provenance/deletion responsibilities.

This forward-only boundary prevents new outbox projections through the configured repository. Historical outbox bodies are unchanged and remain a separate cleanup/admission requirement; do not treat enabling this option as deletion. Direct database writers must be inventoried independently (current collaboration direct outbox inserts already use empty payloads). Unconfigured repositories retain legacy projection behavior and must not be used for new pilot writes after admission.

Synthetic native PostgreSQL tests cover every current event type, nested transactions, actual message/activity/failure flows, no content-capture calls, immutable server options, external publication, owner reads, historical preservation and unchanged default projections. A real repository → event-stream → HTTP → shared client event-source test proves the refresh fallback. Existing Web shared-client, Electron Desktop adapter and content-negotiation tests preserve parity. Runtime surface captures and startup qualification remain the parent stack's gates.
