# App craft guidance

A useful generated app needs a task-specific direction, a real working flow, and rendered feedback. Design instructions alone do not prove visual quality.

## Practices adopted for Matrix

- Invite the user's preferred style, app reference, or inspiration screenshot when the direction is unclear; preserve supplied references through iteration.
- Use bounded similar-app screenshot research, optionally delegated to available subagents. Inspect actual images, compare relevant task screens, and record source/viewport and chosen patterns in the owner project.
- Keep one primary direction in DESIGN.md, with layout/density, tokens, type, interaction states, data fields, and motion purpose. Present annotated alternatives when they help a real choice.
- Reuse Matrix tokens and appropriate components rather than applying the same decorative template to every product.
- Build a complete flow with owner-controlled Postgres through MatrixOS.db, then verify it in the actual sandbox.
- Exercise rendered wide/narrow windows, keyboard/touch behavior, reduced motion, failure states and save-and-reopen persistence. A build alone establishes none of these.

## Comparison validation

Use the same brief across distinct available Claude and Codex models. Record the actual model, loaded skill snapshot, runtime, app paths, rendered evidence and tests. Keep demos isolated from existing apps and use fictional examples.

The owner requested planning, personal finance and creative-studio themes, each with an app and matching landing page. These live comparison builds extend the original implementation plan without authorizing a customer release or replacement of existing apps.
