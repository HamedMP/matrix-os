# Aoede on GPT-Live-1: spike research

Date: 2026-10-06/07. Spike code: `scripts/spike/gpt-live/` (throwaway; delete after qualification no longer needs it).
Two live sessions, 63s and 133s, browser WebRTC + Node sideband, client delegation, fake backend.
Review update: 2026-10-07. No additional provider calls or experiments; the measured observations below are unchanged. They do not establish production wiring, five-minute reliability or restart recovery.

## Decision

Replace both the Gemini Live assistant (`packages/gateway/src/vocal/`, broken: "Could not connect to voice service")
and the `feat/aoede-product-rebuild` branch (~15K LOC chained STT→Codex→TTS, unreliable) with GPT-Live-1
in **client delegation** mode. GPT-Live owns listening, speaking, VAD, interruption, and transport.
Matrix OS owns the backend: transcript context, kernel/Chat runs, actions, approvals, memory.

## Measured

| Item | Result |
|---|---|
| `POST /v1/live/sessions` (WebRTC SDP exchange) | 2.9s; `session.started` ~0.8s later |
| First-token response latency | 400–800ms after the user's last word, every turn |
| Delegation fires | Same millisecond as the final `session.input_transcript.delta` of the utterance |
| Delegation payload | `{ id, type: "delegation", target: "client" }` — no utterance text (as documented) |
| Utterance recovered from buffered `input_transcript.delta` | 3/3 correct |
| Spoken acknowledgement after delegating | 400ms, generated by the model ("Sure, on it") — no code needed |
| `session.thinking.append` | `.appended` in ~800ms, nothing spoken |
| `session.commentary.append` | Spoken ~900ms after send; paraphrased ("Done. Your notes are open."), then continued the conversation unprompted |
| Turn detection through pauses | List with 1s+ gaps between items ("chicken … eggs … and … oats") was treated as one turn |
| Barge-in | User "Wait" while assistant mid-sentence → output stopped before the user's word was transcribed; no code needed |
| Delegation judgment | "Sing me a long song" / "sing in Hindi" handled in-model; action/information requests delegated |
| Long silence | 65s of no speech, session fine |
| Session length | 133s with no degradation; `session.expires_at` present on start |
| Sideband after `session.closed` | Closes with 1006; harmless |
| Billing | `session.usage.updated { seconds }` every ~15s on the sideband; $0.05/min |

## Findings that shape the design

1. **Commentary is trusted verbatim; the model does not reconcile result vs request.** A wrong result
   ("Notes is open" for a weather question) was spoken as-is; on user objection the model apologized and
   asked to repeat rather than detecting the mismatch. Backend results must be correct and
   self-describing ("Weather today: 72°F, sunny"). Never send placeholder commentary; progress goes
   through `thinking.append` only.
2. **Kernel requests need the last few turns**, not only the final utterance. The second delegation's
   utterance was "I asked you what's the weather today". Hand the kernel the last ~3 user/assistant turns.
3. **Delegation and the final transcript delta arrived in the same tick in the spike.** Ordering is not guaranteed;
   correlate transcript intervals with delegation timing. A ~300ms grace is a starting hypothesis to qualify, not a proven turn boundary; output-caption arrival does not prove user speech is complete.
4. **The model self-acknowledges and self-covers backend latency** (6s tested). No ack code, no
   "still working" code unless kernel runs exceed what the prompt prepares it for.
5. **Corrections after a bad result produce no new delegation.** `session.instructions.append`
   (`delegation_id: null`) is the lever if the backend needs to retract or redirect.

## Not tested (qualification required)

- Late results against an old delegation ID: test the original ID and only fall back to null for its correlated rejection. An arbitrary socket failure is not proof the append was rejected.
- Sideband process loss: the provider documents an independent media leg, but **attachment does not replay earlier events**. Do not infer lossless gateway recovery. The revised plan offers a fresh session seeded with bounded saved text and verified Chat outcomes, after closing/finalizing the old session where possible.
- Backend >10s, queueing, approvals and cancellation through real canonical Chat: the fake backend did not exercise these. Only report "started" after actual admission; completion remains tied to persisted run state.
- Sessions >5 minutes, actual expiry value, startup/attach ordering, peer teardown, final usage and reservation settlement. The creation REST response contains session ID and answer SDP; expiry is in subsequent session snapshots, not guaranteed in the mint response.

## Verified documentation and local integration corrections

- [REST creation](https://developers.openai.com/api/reference/resources/live/methods/create) accepts `{ session, transport: { type: "webrtc", sdp } }`, so native fetch and existing `ws` suffice. Do not import the hoisted/transitive OpenAI SDK as an undeclared platform dependency.
- [Sideband](https://developers.openai.com/api/reference/resources/live/sideband-websocket) observes subsequent events, not replay. Frontend event permissions default to allow-all; the plan explicitly restricts them at mint.
- [Session management](https://developers.openai.com/api/docs/guides/live-conversations) supports startup text history (128 messages/8,192 tokens) and graceful close through `session.closed`. An append acknowledgement confirms acceptance, not that speech was played.
- [Billing](https://developers.openai.com/api/docs/guides/voice-latency-cost?api=live) is per-second active duration, including silence/backend work. Initial WebRTC creation bills 15 seconds credited against running duration, not added to it. Usage updates are cumulative replacements; final `session.closed` confirms final seconds. Missing finalization is unconfirmed.
- Local `bots/continuations.ts` supplies the actual canonical admission/queue/revision retry pattern; kernel approvals require platform-minted proof and the authenticated shell HTTP path. `speech/{routes,service,funding,config}.ts` supplies runtime identity and reservation primitives, but Live config/operation policy needs explicit integration.
- Notes' editor prefers nonempty `content_json`, including the empty paragraph produced by hydration. Content-only writes can render blank or stale; keep markdown and rich text synchronized. Existing `/ws`, Desktop handlers and Vocal visibility store are reused, not replaced by another browser event socket.
- The [Ultra review](https://ampcode.com/threads/T-01a11468-15bb-70dc-af67-055ed1d70799) searched upstream issues for replay/duration behavior and found no relevant thread. That is not evidence that no issue exists. The [official console](https://github.com/openai/openai-live-console) avoids automatic billable reconnect and labels missing final usage incomplete.

## Architecture that follows

```
Browser ──WebRTC audio + data channel (captions)──▶ OpenAI GPT-Live-1
   │  POST /api/aoede/session                                             ▲
   │  existing /ws (authorized UI effects, acknowledgements, cards)        │ sideband WS
   ▼                                                                     │
Gateway packages/gateway/src/aoede/ ──▶ Platform funded mint/attach proxy ──┘
   ├─ transcript.ts   bounded delta buffer and owner recovery checkpoint
   ├─ delegate.ts     delegation → quick action | kernel/Chat admitTurn() → thinking/commentary appends
   ├─ actions.ts      open_app / close_app / notes / remember (Zod discriminated union)
   ├─ prompt.ts       Aoede personality + when-to-delegate (ported from vocal/prompt.ts)
   └─ session.ts      funded mint, attach, close; explicit fresh-session recovery after restart
Platform owns credentials, runtime/session binding, wallet reservation and trusted final usage.
Shell submits approval decisions through existing authenticated canonical Chat HTTP routes.
```
