# Customer Browser production lifecycle and admission

## Scope and source of truth

The host bundle stages the built OS Browser UI separately as flat `bin/matrix-browser-ui-*` files so setup remains available before native installation. It also carries a separate `matrix-browser-runtime.tar.gz` containing reviewed supervisor/native-window modules, the built viewer, and the fixed native service definitions. It excludes the Preview installer/guard, owner app manifest, optional agent-browser/browser-use experiment runners, dependency stores, profiles, cookies and credentials. The existing `matrix-install-browser-preview` and exact Preview target guard remain unchanged.

The checksum-verified host-bundle updater and initial provisioner install the stdlib-only Python lifecycle helper into `/usr/local/libexec/matrix-browser-runtime.py`, root-owned and read-only. The root systemd unit executes that protected helper through `/usr/bin/python3 -I`. It does not import or execute scripts from the owner-writable app directory. Root-owned release metadata is the committed artifact authority. `app/BUNDLE_VERSION` is intentionally owner-writable and is compared only as bounded version data, never trusted as executable provenance.

The helper validates every privileged source and ancestor with `lstat`/`O_NOFOLLOW`, root ownership and non-writability. Fresh/golden hosts have `/opt/matrix` root:matrix mode 0770; reconciliation removes group write on this OS container and OS bin/env containers non-recursively. Child ownership, app write permissions and owner data remain intact. The runtime archive SHA-256 is checked against its root-owned, non-writable checksum sibling. Both files arrive through the checksum-verified enclosing bundle and privileged installer; an owner-writable checksum is refused. Runtime archive extraction rejects links, traversal, special files, duplicate names and bounded-count/size overflow. Root configuration uses an allowlist of six native units, `tint2rc`, and the exact nginx site. All extracted JavaScript runs as `matrix`, never root.

## Lifecycle and failure states

The host identity gate requires a valid customer handle, machine UUID, Clerk owner, matching optional owner projection and `primary` runtime slot. Preview handles/slots are rejected. Explicit `MATRIX_BROWSER_LAB=false` is an opt-out checked before dependencies or credentials change. Initial setup requires at least 2 GiB physical RAM and 2 GiB free disk. Each committed version has a protected three-attempt status record; systemd also caps starts to three per hour. Exhausted attempts stay visible as `exhausted` rather than retrying forever. The owner-authenticated setup API invokes only fixed `--status` / `--retry` commands on the protected helper. They return coarse `{status, retryAvailable}` JSON without credentials, page state, file paths or native errors. A durable root-only retry journal permits one explicit retry per release per hour, resets the three-attempt budget, and asynchronously starts the fixed lifecycle unit. Retry honors opt-out, keeps a ready runtime running, and consumes its budget before service calls so command failures cannot create an unbounded restart loop. A new release resets the budget. Stored-ready status performs one fixed, two-second `systemctl show` for all six native units and validates exactly six known states (ignoring output separators). All-active remains ready; stopped/failed units expose safe failed status and the same bounded explicit Retry; transitional units show installing without a retry. Explicit retry clears start limits for the lifecycle and only fixed native units whose installed files validate as root-owned, regular, non-symlink and non-writable before scheduling the lifecycle. Missing native unit files are expected before first installation and omitted, while unsafe files or actual reset errors fail closed; it does not itself restart healthy Chrome or change profile/credentials. Explicit Reconnect rechecks the current Computer’s setup state before viewer admission; failed setup exposes bounded Retry in the same window. A ready result retains the mounted surface until the existing viewer reconnect proceeds. Healthy setup is not continuously polled and viewer failures do not trigger automatic setup retries. This is a bounded activity check, not continuous health polling or a full viewer/CDP probe.

1. Initial provisioning starts core services before scheduling the optional Browser oneshot asynchronously. The shared scheduling lies outside the clean-image/exact-golden-snapshot branch, so first-owner activation uses the same identity checks and credential initialization. Golden builders retain only immutable bundle payload/program bytes: sanitation stops/disables any Browser units, removes the entire runtime prefix (viewer credential pair, pending/activation journals, status, installed-release and payload), native unit files/enablement, and owner profiles. Both clone activation and validation require the new clean-state evidence and reject inherited runtime state. Synthetic golden activation does not enable Browser or manufacture a customer owner. Each real owner clone creates its own credential pair; repeated updates preserve it. Failed native setup retries through systemd and does not gate Matrix readiness.
2. Host updates wait for any current Browser reconciliation lock before stopping the lifecycle unit. Chrome/display services and profile remain live. New Browser reconciliation is scheduled only after core gateway/terminal health succeeds and release metadata commits. A rejected core candidate cannot install its native Browser experience. The existing host transaction snapshots bin/runtime payloads and now also the protected Browser helper; core failure or manual rollback restores those bytes, including removing a newly introduced helper when the prior release had none. After healthy core rollback to a Browser-capable release, the restored lifecycle asynchronously reconciles the restored native payload. Rolling back before this production Browser capability existed can make its UI unavailable; it retains native/profile data and does not uninstall OS packages.
3. The helper rechecks committed release/version before activation, preserves any existing viewer credential pair, and refuses inconsistent legacy pairs rather than rotating them. A root-only pending credential journal lets interrupted first-time publication finish the same pair. New credentials stay server-side; they are never returned in logs or client JSON.
4. Native code/config activation is journaled in the root-only prefix. Atomic state writes fsync file data, replace the destination and fsync its protected parent; newly created protected directories and hardened directory metadata are synced as well. Activation syncs the complete bounded incoming payload tree, durably publishes its journal before app swaps, then syncs both parents of each rename. Recovery also syncs namespace changes before retiring its journal. Activation and credential journals are unlinked with a parent-directory fsync only after their replacement state is durable; previous runtime cleanup happens after durable activation-journal retirement. Durability failures stop forward progress and prevent previous-runtime cleanup. A journal unlink may already be visible when its parent sync fails; recovery must still preserve a complete old or new runtime. It retains the previous app, prior unit/nginx bytes and the previous value of its owned Browser enablement key until native health and gateway restart pass. Failure or interruption restores the previous runtime/config before retry. Recovery runs before attempt-budget and opt-out early exits, including after an interrupted third activation; exhausted budget still prevents new install attempts. Environment rollback restores only Browser enablement; native activation never writes or removes origin configuration. It preserves current operator origin changes/removals, the current viewer credential pair, identity, funded routing and other current keys, and keeps a current explicit Browser opt-out false. A first-install failure may leave native packages and a generated credential pair, but Browser remains disabled and core services remain usable. Completed payload/dependency staging directories are deleted; abandoned root-owned staging is capped and expires after one day without following symlinks.
5. An unchanged, healthy installed release is a no-op, including while a legitimate agent holds the human-input gate. Normal upgrades retain native Chrome/display PIDs when their fixed units are unchanged and restart the supervisor. Explicit unit changes can restart affected native services; Chrome uses graceful stop and its persistent owner profile. Preserve the established `/home/matrix/.local/share/matrix-browser-lab/chrome` path, including cloud-init's exact `/home/matrix/.local` → `/home/matrix/home/.local` alias. Other profile-path symlinks are refused. The gateway home mirror hard-excludes `.local`, including when an owner ignore file tries to re-include it; this profile is not mirrored even on hosts with that canonical alias. Profile contents, credentials, owner apps, OS settings, home files and Postgres are never copied, reset or recursively chowned.

The first install supports Ubuntu 24.04 x86_64. Unsupported distro/architecture/resource checks run inside the persisted attempt boundary, so failures settle to failed/exhausted. If an installer is killed while its record says installing, status checks the fixed unit state and reports failed/exhausted once inactive, permitting bounded recovery. Physical `MemTotal` and free storage are measured; marketed capacity alone is not evidence of passing preflight. Before any all-user rollout, inventory the actual OS/architecture/RAM/storage cohorts. Hosts outside this matrix remain explicit rollout blockers with a reviewed support/remediation decision; this change does not resize or buy capacity. KasmVNC 1.5.0 is SHA-256 pinned. Necessary desktop packages use the OS package manager. Chrome downloads use the fixed official HTTPS stable package URL with bounded transfer/retry and record the downloaded package SHA-256 in a protected dependency marker. **Chrome and distro dependencies are installed separately from immutable host-bundle bytes; they are not reproducible native package artifacts and OS package changes are not reverted by app/config rollback.** Optional browser-use Python and agent-browser engines are deferred: the canonical production Browser uses the shared CDP broker. Native dependency/first-install validation on a real customer-equivalent Linux host is required before promoting this change.

## First upgrade from a pre-Browser updater

A build-inlined reviewed Python bootstrap binds the helper, native archive, checksum and lifecycle unit SHA-256 values to the final release version and git commit. After an old updater commits core health and restarts, the new startup runs it only after interrupted recovery, with no pending phase marker and a matching actual running gateway. It validates the bound primary customer identity and explicit opt-out without mutation, then non-recursively hardens historical root-owned OS container directories, pins root ancestors, snapshots regular root-owned source bytes and verifies their embedded digests before installing protected helpers. A protected Computer/owner-bound receipt permits one asynchronous lifecycle start without resetting its native retry budget. Failed scheduling leaves no success receipt and can retry on restart; golden sanitation removes bootstrap receipts. Explicit opt-out, owner profiles and core readiness remain authoritative. Legacy bundles without the payload are a no-op; mismatched release/app/hash, symlinks and writable foreign ancestors fail closed. The regression exercises the old commit/install/restart path and generated new bootstrap with the native-service boundary replaced by a fixture; this is not live Linux installation acceptance.

## Native health and viewer transport

All six native services run as the owner account. VNC viewer port 6901, supervisor port 8730 and Chrome CDP port 9222 must all be present on loopback; any public binding on those ports fails health. CDP must return its exact loopback WebSocket URL, native window status must report Chrome present and a boolean human-input gate state, and the viewer must complete an authenticated WebSocket 101 handshake with a matching accept key and binary protocol using the retained server-side credential. Public native RFB port 5907 also fails health. Health requests use fixed loopback URLs, no ambient proxies or redirects, bounded responses and timeouts. Chrome keeps its sandbox enabled and its established persistent profile path. Native readiness accepts the supervisor’s real cold-start `humanControlAvailable=false`, as well as a deliberate agent-held input gate: health never enables pointer/key input or synthesizes owner interaction. Browser session/takeover authority remains responsible for human-input changes.

The existing nginx `/apps/` proxy does not forward WebSocket upgrades. Production reconciliation adds only the exact `/apps/browser-lab/viewer/websockify` upgrade location pointing to the authenticated gateway; `nginx -t` and reload occur within activation and restore on failure. No native port is exposed directly, and no owner app manifest or app nginx route is created.

## Session admission and authorization

| Boundary | Authority | Failure behavior |
| --- | --- | --- |
| Lifecycle/root configuration | Verified bundle, protected root helper, root-owned committed release metadata | Refuse unsafe/incomplete sources; retry without enabling Browser |
| Browser setup status `GET /api/browser/setup` | Verified runtime bearer and matching trusted primary owner; valid machine UUID, handle and Clerk owner | No-store coarse status only; missing/invalid helper yields generic unavailable |
| Browser setup retry `POST /api/browser/setup/retry` | Same owner identity plus required allowed Origin; strict empty JSON object with 4 KiB streaming body limit | Fixed sudo helper invocation bounded to 5 seconds / 4 KiB output; root one-retry-per-hour budget and opt-out preserved |
| Browser OS app session/session-token | Verified runtime bearer and matching authenticated principal; pre-enable setup admission additionally requires validated primary identity and trusted setupOwnerId | Owner mismatch refused; native/viewer authorization remains feature-gated |
| Runtime identity | JWT handle/runtime slot verified by the existing upstream authentication boundary | No user header or app manifest may invent runtime identity |
| Viewer launch | Existing per-runtime HMAC cookie, one-use launch token, scoped gateway app session | Preserve session/CSRF/origin checks and bounded ticket lifecycle |
| Native viewer/control/CDP | Authenticated gateway and fixed loopback routes | Preserve SSRF/control checks; no public CDP or viewer forwarding |

Canonical `browser-lab` session admission and its setup UI are OS-owned for a validated, trusted primary owner before native activation. The built UI is staged into root-installed flat `/opt/matrix/bin/matrix-browser-ui-*` files, covered by the existing host-bin copy/rollback transaction independently of native payload activation, and presents Browser setup, loading, failure and bounded retry states across Web Canvas, Web Desktop and Electron Desktop. Setup Origin authority is resolved before native activation for a validated primary customer: preserve explicit `SHELL_ORIGIN`; otherwise use the configured `MATRIX_PUBLIC_APP_URL` only as a strict HTTPS origin, defaulting to `https://app.matrix-os.com`. Native activation and rollback never write or remove `SHELL_ORIGIN`, so a configured app origin remains valid across setup-to-ready transitions. Never derive trusted configuration from request Origin or Host. Native Browser API/viewer access remains gated on enabled owner-bound broker composition. Obsolete hashed UI assets are snapshotted in that transaction and removed on installation; rollback restores them and removes newly added assets. Only the entry and allowlisted flat assets are mapped to the fixed UI prefix; other host-bin files cannot be served. Electron setup responses are discarded if the token, runtime origin or auth generation changes while they are in flight. The exact canonical OS route cannot be shadowed by an owner app of the same name; other apps retain their manifest policy. Existing guarded Preview admission remains unchanged. It does not write an owner app manifest, grant arbitrary apps Browser access or change supervised authority. Full Access Browser and supervised tool authorization remain separate. Supervised general enablement still needs its explicit runtime acceptance.

## Release and regression gate

The implementation must ship through its own Conventional Commit PR, required CI and Greptile 5/5. Production Electron support requires a paired Desktop release containing the Browser setup bridge capability. Installed Desktop 0.1.16 predates that capability and cannot qualify this new route; the hosted UI shows an explicit Desktop update prompt on older native bridges without sending unsupported setup requests or admitting the viewer. Web setup and Preview diagnostics keep their own existing routes. Qualify the new signed Desktop artifact together with the candidate host bundle; publishing either is outside the current fixes/tests/PR-only approval. Qualify the exact candidate first on Main Computer and signed Electron Desktop, capturing source SHA, immutable artifact checksums, runtime health, UI evidence, native input/focus/background behavior, reconnect, Chat/provider basics, Settings and retained data. Promote stable and run reviewed per-target production deployment only after those checks pass. Retain the prior stable and exact per-host version for rollback; preserve the native profile/credential state during an exact-version rollback. Report merged, published, installed, enabled and accepted states separately.

The canonical public documentation follow-up is a separate PR in `FinnaAI/matrix-os-site`, documenting supported Browser behavior, availability/install retry semantics, retained owner browser data and platform limitations after live acceptance. This implementation spec is not evidence of successful production installation or runtime acceptance.
