# Data model and authority

All additions use PostgreSQL/Kysely. Table names below are proposed; do not duplicate equivalent tables discovered when rebasing. Platform migrations use `runPlatformMigration`; owner migrations extend the existing collaboration bootstrap through extracted modules. No new database engine or independent ACL service.

## Identity types

- `ActorId`: immutable Clerk user ID, mapped through existing platform identity records; never a handle or org ID.
- `OwnerRef`: `{ type: personal|organization, id }`. Existing personal IDs retain their value; org IDs are immutable Clerk org IDs.
- `PayerRef`: a billing-account ID resolving to one personal/org principal. Never infer it from the current administrator or Share audience.
- `ResourceRef`: `{ kind: chat|terminal|project|app|file|folder, id }`. File IDs are stable catalog IDs, not caller-supplied absolute paths.
- `AudienceRef`: `{ type: user|organization|group, id }`. Groups belong to exactly one organization.

Extend billing subscription/entitlement, funded budget/reservation/settlement and audit records with `billing_account_id`, `actor_id`, `owner_type/id`, scope/runtime reference and payer-policy revision as applicable. Backfill personal accounts before changing reads; retain legacy personal key fields as compatibility projections until all readers migrate. Stripe event IDs and request/reservation IDs remain unique. Never move an existing personal subscription to an org by editing its user ID.

Extend platform collaboration discovery with audience index entries `(scope_id, audience_type, audience_id)`, OwnerRef, generation and safe admin metadata. This is a routing/search projection, never authorization. Hydration rechecks live grants. Org-admin inventory indexes only org-owned or org/group-addressed resources; unrelated direct-user grants remain absent. Removing an inbound org grant writes a platform denial fence first; an offline owner cannot keep it accessible or resurrect it by replaying old directory events.

Existing `collaboration_members` becomes a compatibility projection for direct user invitations and personal owner display. It is not a fallback allow path once `authority_version=2` activates. It must not expand an org audience or constrain org size to eight people.

## Authorization result

`AuthorizedCollaborationContextV2` carries actor, OwnerRef, resource and membership scopes, effective resource role, explicit capabilities, matching grant references, scope/grant revision, org/group/membership generations, evidence expiry, runtime authority generation, and optional server-resolved sponsorship reference. Management and billing capabilities are distinct from editor/viewer. Personal owner retains current powers; current org admins administer org-owned scopes. Org admins receive only metadata/removal powers over personal resources shared into their org, not content/edit/transfer rights.

For org-owned resources: a current org admin may manage metadata/grants/lifecycle; content read/edit still requires a matching resource grant. An admin may explicitly self-grant with an audit record. Other current members need matching grants, and guests need both accepted guest admission and a matching direct grant. A former member's direct grant cannot bypass removal. For personal resources, independent accepted user grants can survive departure from an org and must appear in the effective-access explanation. Match org/group audiences dynamically, intersect with lifecycle and legacy action ceilings, then union permitted actions; a denied/expired grant contributes nothing.

## Transactions and failure states

1. Owner write order: lock membership root scope → affected child/catalog roots in sorted ID order → grant/operation rows → resource write. Recheck epoch/revision in the write statement, not only a pre-read. Actor evidence must still be valid when the authorized write is admitted. Accepted pre-revocation work is separately fenced before its next side effect.
2. Platform write order: org → group/member/guest → command/denial fence → audit/outbox. Epochs increase monotonically. Never perform Clerk/Matrix/Stripe/R2 calls while holding a database transaction.
3. No cross-database atomicity is assumed. Short-lived evidence, platform denial fences and gateway epochs enforce access; outboxes reconcile indexes/rooms. Revocation completion means the authoritative local fence has committed and affected runtime permits have been invalidated/expired, not merely that a webhook was queued.
4. Transfer phases: `prepared → staging → fenced → committing → active`; error yields `blocked|recovering`. Source remains authoritative until the versioned cutover; then it is an inaccessible labeled backup. Two writable authorities are never acceptable. Transfer moves only explicit owned content, not credentials/private drafts/personal memory; payer changes require their own confirmed sponsorship.
5. Staged uploads/copies, unapplied directory entries and blocked Matrix bindings are acceptable inaccessible orphans with TTL/reconciliation. Active stale grants, double charges, silent partial exports and room access without its enforcement gate are not.
6. Org deletion first denies org access/new spend, then queues export/retention handling under an explicit configured policy; no immediate destruction inferred from a Clerk delete event. Preserve an audit/recovery operator path. Last-owner/admin removal uses Clerk's configured creator/admin constraints plus an application check; do not manufacture an unremovable membership outside Clerk.

## Concrete identity, publication and migration rules

- Catalog IDs are never reused. Store `incarnation`, `parent_catalog_id` FK, `scope_id` binding, `authority_parent_scope_id`, normalized relative path and deletion tombstone. Unique live `(owner_type, owner_id, normalized_path)`. Recreate at the same path creates a new UUID/incarnation and no old grant. Use slash-separated NFC paths, reject normalization/case collisions on the target filesystem rather than silently merging; descendant moves update parent/path bindings under the same confirmed root transition. Containment in a private project is not inherited authority.
- App instances carry `source_installation_id` and unique source/incarnation mapping. Backfill a live slug installation once; reinstall produces a new incarnation. Existing slug readers/writers must resolve the adopted instance after activation. Namespace provisioning has `pending/ready/failed/recovering` state; orphan DDL is inaccessible until reconciled. Deletion/export includes only that instance's namespace/artifact references. App data and ACL mutation must use the same physical owner Postgres transaction; if a current bridge cannot supply it, keep the app ineligible until a transactional adapter exists.
- File bytes are not in the SQL transaction. Journal `prepared → staged → publishing → committed` with old/new content identity and catalog/manifest revision. Stage inert bytes first. Reacquire current platform evidence outside the final SQL transaction; lock and CAS the owner/catalog/grant epoch, then atomically publish the declared version under an exclusive root write fence. While SQL and filesystem rename/manifest flip disagree, readers/writers for that resource return recovering/unavailable. Restart compares journal+content hashes to finish the declared publish or restore the old version; it never guesses from a path alone. Staged orphans are TTL-cleaned, old authoritative bytes remain until final recovery verification. Test crashes before/after every SQL/rename/manifest step.
- Platform `organization_access_permits` records request/actor/scope/audience generation, immutable expiry, issued/completed/revoked status and runtime acknowledgement. Expiry is never later than its original evidence deadline. Denial fences stop new permits. Long work stages effects and obtains a new permit before publication; it may not carry an expired permit into a later commit. Same-DB mutations have transaction/statement/lock timeouts bounded by remaining permit time (with clock-skew margin) and final epoch/deadline predicates. Platform network calls stay outside DB transactions. Revocation completion waits for outstanding admitted permits to finish/acknowledge or expire, plus the runtime fence; a queued invalidation alone is insufficient. Already admitted external effects are recorded separately from later denied side effects.
- Before any V2 scope activation, deploy a compatibility release that refuses V2 scopes in all legacy readers/writers, and verify all serving runtimes against a minimum protocol version. Store migration checkpoint/block reason per scope; ambiguous imports cannot activate. After activation, direct-member compatibility projections update transactionally with user grants, but every authorization reader must use V2. No old binary may serve a V2 scope; rollback disables/reverts to another compatible binary rather than restoring old ACL reads.

## Billing migration and consent inventory

Migrate/backfill `billing_customers`, `billing_subscriptions`, `billing_entitlements`, `billing_checkout_attempts`, `prebilling_provisioning_intents`, `billing_trial_accounts`, `billing_entitlement_overrides`, runtime action records, `ai_credit_checkout_claims`, funded policies/balances/restrictions/reservations/ledger in explicit checkpoints. Personal trials/support overrides remain personal; org trials default disabled without approved catalog policy, and entitlement overrides remain operator-controlled. Update `billing-status-route.ts`, prebilling coordinator/store, `billing-runtime-action-store.ts`, checkout/portal/Stripe projection and credit consumers before final constraint changes. Dual-write personal compatibility only during transition; compare reads and never select the acting admin's customer as an org fallback.

AI charges use resource sponsorship when an explicit, current scope sponsorship exists; otherwise the runtime sponsorship applies. A different scope payer is allowed only with both the resource owner's authenticated consent and that payer's admin approval. Personal owner consent is a signed, single-use, expiring receipt issued by the owner gateway after an authenticated owner operation and bound to scope, payer, budget/policy revision and request; an org admin's assertion is insufficient. Runtime hosting charges always use runtime sponsorship. Capture chosen payer and sponsorship revision immutably at reservation; settlement/refund/dispute applies to that original payer after later switches. Balance/policy/restriction keys include billing account; reservation/ledger keys include request ID, billing account and sponsorship revision with runtime/scope attribution. Never migrate accrued usage when a sponsorship changes.

Webhook inbox rows retain a sanitized durable envelope (event ID/type, immutable org/actor/membership target IDs, occurrence/receipt timestamps, payload hash and processing state), not an unspecified payload reference. Reconciliation refetches current Clerk state. Upsert platform identity/profile records for members who have no personal runtime; membership and sharing do not require provisioning a personal machine.

## Matrix service identity lifecycle

`organization_matrix_service_identities` has one org-scoped service MXID, secret-manager reference, key version, active/rotating/revoked state and rotation timestamps. Never reuse human/AI tokens from `matrix_users`. The service credential can reach only that org's managed rooms. Rotation pauses admissions, replaces the credential through supported provider APIs, validates the replacement, revokes the old session and resumes; unknown outcomes stay unavailable. Org/group deletion immediately disables Matrix OS access and archives the binding. After configured retention/export completes, the service leaves/forgets the room and credentials are revoked; any homeserver-side purge is a separately configured operator action, not a fictional room DELETE endpoint.
