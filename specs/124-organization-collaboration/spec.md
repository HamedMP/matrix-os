# Organization collaboration on member computers

**Status:** Revised product specification for review; implementation is not started.
**Date:** 2026-09-20
**Baseline:** inspected main `94985f02e`; planning branch `codex/org-collaboration-spec`. Source inspection is not production validation.
**Decision:** owner-hosted project + shared group Chat + one owner-selected AI source + owner-controlled Git; direct transport and one coordinated cutover; no organization-wide computer requirement. Sharing exists only inside an organization; the organization is the only gate, and the legacy release flags and rollout cohort are removed rather than switched on. Transport is the platform as a transparent relay with all authorization on the home computer; direct client-to-home connectivity is a later, compatible upgrade. Members may prompt the owner's AI on the owner's configured source when the organization enables it; provider-terms responsibility rests with the owner. V1 grants whole-project presets only, needs no owner approval for Git operations, creates no per-Chat worktrees, delegates no integrations, and ships on Web Canvas, Web Desktop and Electron Desktop with Native Mobile and CLI recorded as an explicit V1 limitation. V1 is the minimum functional organization collaboration: Clerk membership is the only organization concept; organization administration, groups, guests, invitation quotes, billing, sponsorship, member-assigned computers, computer-to-computer transfer and managed Matrix group text are deferred.

## Product and placement

Members share a project, Chat, terminal, live app instance, file or folder with their Clerk organization or specific current members of it. Each of these resource types is shareable on its own in V1 with the same two presets. A standalone share grants only that resource (a folder share includes its contents), never the enclosing project. The readiness preview shows only the items that apply to the shared type: owner AI source and submit mode for projects and Chats, owner Git identity and Chat root inventory for projects and for Chats with an execution root, and none of these for files, folders and app instances. There is no sharing outside an organization: every shared resource is bound to exactly one organization context, and every grant resolves against that organization's current membership. Every resource has one authoritative home computer. Content, Postgres data, AI execution, worktrees, PTYs, integration execution and realtime fanout stay on member computers. Opening a resource does not require the recipient to own a computer.

An organization is an identity and membership boundary. It is not a shared VPS. Existing personal computers host member-owned shared resources; the share itself is always scoped to one organization, and the resource stays owned and hosted by the member who created it. Organization sponsorship, member-assigned computers, org-controlled recovery and org-owned resources are deferred; do not claim creator-independent durability in V1. No pooled org computer, org-wide desktop, automatic machine conversion or fleet placement scheduler is required.

Keep actor, resource owner, host owner, assigned member, credential owner and payer distinct. A recipient connects to the resource's home, not a copied project on their own computer. Offline hosts show unavailable; no implicit new authority or writable replica is created.

## Clarifications

### Session 2026-09-20

- Q: Which capability presets ship in V1? → A: Viewer and Contributor only; Discussant and Maintainer are deferred with the granular vocabulary.
- Q: Which resource types can be shared on their own in V1? → A: All of them: project, Chat, terminal, live app instance, file and folder are each shareable standalone with the same two presets.
- Q: Does an organization-wide share add every member automatically, or does each member join explicitly? → A: Explicit join; the share is pending in each current member's `Shared with me` until that member opens it.
- Q: Who may cancel a shared AI run? → A: The requesting member and the project owner only; audit records which one cancelled.
- Q: When the home loses track of a shared run (bundle update, reboot, crash, partition), what do members see? → A: The executing run is marked interrupted and its requester resubmits; queued requests are preserved and start automatically once the home is back and the requester's membership is still fresh. Reattaching to a surviving run unit is deferred.

## Opinionated first-release experience

1. The owner shares a project with their organization or specific members of it and chooses one of two presets: Viewer or Contributor. The default Contributor preset covers the whole project; granular restrictions are deferred.
2. Accepted contributors join the same default project group Chat, with named human messages. Discussion never automatically starts AI work. Viewers can follow but cannot post; the Contributor preset includes discussion.
3. Everyone sees one canonical conversation, files and run queue on the owner's computer. When the organization enables member AI submission, any member with the Contributor preset can explicitly request AI work through the owner's configured project source, whatever kind of source it is; the owner may restrict a project to owner-only submission. Which applies is visible before joining.
4. The host executes the selected Codex or Claude harness locally. One run at a time per Chat; joining requires no additional Chat or worktree, and creating per-Chat worktrees is deferred.
5. The project owner controls Git identity and remote credentials. Commit, push and PR operations run through the host's scoped Git broker using the owner's configured author and forge credential; in V1 a Contributor performs them without owner approval. Everyone sees the requesting human, the run and the outcome in Matrix audit.

Default project Chat creation is idempotent and binds the project audience. An organization-wide share never adds members automatically: it appears as pending in every current member's `Shared with me`, and a member becomes a participant only when they open it. Members who join the organization later see the pending item on arrival; members who never open it are never listed as participants. A new member's join preview includes existing shared Chat history. For a member with narrower data access, a Chat must use a data ceiling readable by its entire audience; mixed-sensitivity history requires a separate restricted Chat or reviewed history publication, never silent disclosure. This keeps the default full-project group experience simple without making advanced restrictions cosmetic.

## UI baseline: the confirmed collaboration UX

The interaction model confirmed by the product owner on 2026-09-17 in `specs/525-collaboration-ux-redesign` (implementation log, "Confirmed Interaction Model") is the collaboration UI for this release. Shared Chat uses the ordinary Matrix timeline, composer, AI rendering and responsive frame; human discussion is a right-side in-session drawer on desktop and a full-height bottom sheet on mobile; access is one compact summary popover with an owner-only second-level manager; `Shared with me` is a first-class Chat navigation row with a bounded pending badge; shared terminals keep the ordinary terminal viewport with compact access, discussion, role and controller controls. The shipped components under `packages/ui/src/collaboration/` and `shell/src/components/collaboration/` are the starting point.

124 adds state and controls inside that chrome on Web Canvas, Web Desktop and Electron Desktop. Native Mobile and CLI are an explicit V1 platform limitation: the shared Chat and terminal they already have from 525 keep working, and the new organization audience, readiness and Git-identity states reach them in a later release. It does not introduce a new collaboration header, transcript, composer, composer mode switch, share dialog, inbox or discovery surface. Implementers do not change the confirmed model on their own; a change to it is a product decision recorded in this section before the affected packet starts.

## Identity and permissions

Clerk is authoritative for organization membership. Matrix owns project/resource grants, capability profiles and connection delegation in owner-controlled Postgres. Matrix room membership never grants access to projects or funding.

V1 uses Clerk's default organization roles and needs no custom permissions: any current member can be an audience, and the resource owner alone manages that resource's shares. Organizations and their members are created and managed in the Clerk dashboard by the organization owner; there is no in-product organization administration, invitation, group, guest, billing or audit surface in V1. Admins have no content privilege and cannot read member-owned shares merely because they administer the organization. Unknown roles deny nothing in V1 because roles carry no application authority; the custom-permission vocabulary is deferred until an administration surface is specced.

V1 grants one preset for the whole project and ships exactly two presets. Viewer reads Chat history, discussion, files, app views and terminal output and cannot post, submit, mutate or run Git operations. Contributor adds discussion, AI submission when the effective submit mode allows it, file and app mutation, and commit/push/PR through the Git broker. Discussant and Maintainer, along with the per-folder, per-app, per-command and per-integration selectors in the table below, are deferred; the table is retained as the target capability vocabulary in which presets expand into explicit capabilities. Grants name audience, preset, policy version and expiry. A share preview explains exactly what this recipient can do:

| Capability family | Granularity |
| --- | --- |
| Content | file/folder IDs with read/write/create/delete/export; app instance and read/mutate actions; specific Chats and history visibility |
| AI | submit/cancel own run, steer, model/harness selection, approved funding sources, spend ceiling |
| Worktrees/Git | create/use worktree, inspect changes, commit, merge, push, delete; main checkout protected separately |
| Commands | approved task profile (executable, validated arguments, cwd, environment, network and mounts); unrestricted sandbox shell is an explicit stronger permission |
| Integrations | connection ID, tool/action IDs, read/write/send/delete, upstream resource scope, approval and credential owner consent |
| Management | invite, change policy, approve specific actions, transfer, publish; independent of content editing |

Effective access is lifecycle/fresh membership AND union of applicable allows AND mandatory org/resource ceilings, minus explicit deny rules. A deny always wins across overlapping grants. Every grant derives from one organization's current membership; departure or removal ends every grant derived from it. No grant outlives membership and there is no personal grant path. UI explains the ended access.

Deferred from V1 (retained as the target design for granular sharing): This deliberately supersedes 121's unconditional all-contents access and the previous draft's prohibition on child restrictions. Project membership covers the project structure; inherited defaults may be narrowed by folder/app/Chat capability restrictions. New children inherit parent defaults and restrictions. Child grants cannot widen a parent ceiling. Moving resources requires an access-impact preview and fenced commit. Existing grants migrate with their exact action ceilings, never a silent broadening.

## Direct transport and cutover

In this specification, *direct* means the home computer is the sole authorization point: the platform makes no per-request allow/deny decision, parses no collaboration payload and logs no payload. In this release the bytes still traverse the platform as a transparent relay, because customer VPSes are reached through existing `app.matrix-os.com` session routing, run self-signed certificates and have no per-user hostnames. Direct client-to-home connectivity (per-home hostname plus browser-trusted certificate) is a later upgrade that must not require a protocol change.

The platform authenticates actors, resolves endpoints, manages Clerk projections, issues short-lived scoped proofs, distributes policy epochs and tracks billing. Its relay terminates TLS and forwards collaboration transcripts, PTYs, app payloads, file bytes, worktree patches and peer migration payloads as opaque bytes: no authorization decision, no schema parsing, no payload logging or tracing, coarse byte/connection limits only. Payload privacy from the platform is therefore an operational policy in this release, not a cryptographic property; do not market it as such. Current managed Matrix AI inference and explicitly vendor-hosted connectors remain named external data-processing paths; direct collaboration does not remove those services or imply end-to-end provider secrecy.

Browsers and native clients obtain a resource-scoped ticket and connect by HTTPS/WSS to the origin the resource directory returns, which in this release is the platform relay routed to the registered home. Clients never hardcode an origin. Tickets bind the logical runtime ID and authority generation, never a TLS hostname, and the home verifies them identically whichever ingress delivered them. Computers use authenticated HTTPS sessions with runtime identity and an actor-delegated operation ticket. Tickets never substitute for gateway-local resource checks. No generic owner session is issued to a collaborator. TLS endpoints, CORS/origin checks, replay resistance, key rotation, request/stream limits and expiring membership evidence are mandatory.

Every enrolled customer VPS is eligible in this release through the relay; no per-home hostname or browser-trusted certificate is required. Private/local computers, automated NAT traversal and mesh VPN remain future transport options. The relay is the transport, not a fallback; what is removed is platform-side authorization. Revocation push is paired with fixed-expiry leases, including long-lived streams and tool execution.

All applicable clients and serving runtimes switch together after backup, migration and validation. Remove per-request platform authorization, policy lookups, body parsing and V1 proof/ACL fallback from the proxy and WebSocket bridge, leaving a transparent byte-forwarding relay for HTTP and WebSocket. Preserve user data, stable IDs, personal non-collaboration billing and public snapshots. Sequential development PRs are allowed, but there is one release acceptance gate. Rollback uses a direct-protocol-compatible build or makes collaboration unavailable; it never restores a permissive legacy reader.

## Release gating: the organization is the gate

The legacy collaboration release controls are removed, not switched on. That covers the `MATRIX_COLLABORATION_ENABLED` environment flag (platform wiring, gateway wiring, system info, the customer-VPS cloud-init template and the platform deployment workflow), the platform `collaboration_rollout_policy` table with its milestone/mode/cohort allowlist, the gateway policy client and every cohort or milestone check in authority, WebSocket, terminal and shared-AI paths. Because the flag was written once at provisioning and never rewritten, deleting it is cheaper and safer than fleet-wide flipping: existing `host.env` values become inert and no in-place rewrite is required.

Collaboration wiring always constructs. The organization precondition is a hard authorization check on every collaboration route, WebSocket upgrade, queue claim, tool invocation and integration action: an actor without current membership in the resource's organization is denied regardless of Clerk session validity, direct reachability or selected org. Missing signing or origin configuration fails closed with a logged generic denial; it never skips a check and never opens a route. The same rule covers the implementation window: S20 lands before the S03 membership projection exists, so until a registered, healthy membership source answers for an organization the precondition has no positive evidence and denies every collaboration request. Customer VPSes ship today with the flag hardcoded off; S20 turns that unconditional off into an unconditional deny that only fresh membership evidence can lift, so there is never a deployment in which collaboration serves without the organization gate. No gradual-rollout mechanism replaces the cohort. If staged access is required, it is an organization-creation entitlement on the platform, not a collaboration cohort.

Person-to-person sharing was never enabled on customer VPSes. Cutover inventories any person-to-person scope, grant or invitation record on platform and gateway databases; the expected count is zero. Any record found is terminated with notice or explicitly re-homed into an organization by its owner. Nothing is silently orphaned or auto-converted.

## One owner-selected AI source

V1 has one owner-selected funding/account binding per project, resolved through existing Provider V3. Collaborators see “Runs on the owner's computer; funded by [configured source]” and do not need to add AI accounts. The owner can change the binding between runs using existing account settings; there is no collaborator account picker, subscription pool, per-actor sign-in on the host or quota-driven account rotation. Existing personal multi-account settings are reused only for owner selection, not expanded into a new collaboration subsystem.

Member submission is governed by two owner-side settings, both fail-closed. First, the organization enables member AI submission through Clerk organization public metadata (`collaboration.aiSubmission = "members"`), set by the organization admin in the Clerk dashboard and projected by the platform membership projection; absent or unknown means owner-only. Second, the project owner may restrict any project to owner-only submission in its execution policy; the default follows the organization. When both allow it, members submit runs on the owner's configured source exactly as the owner does, including personal subscriptions: inside an organization people trust each other, and Matrix does not enforce provider eligibility. Matrix does show the source kind to every participant ("Runs on the owner's computer, funded by the owner's Claude subscription") and records the owner's acknowledgement that the selected source's provider terms are the owner's responsibility. Never silently switch to a different source when the selected one is unavailable.

The project owner chooses model/harness, permitted submitters, budget and integration/task profile once. Organization sponsorship of the source and org-sponsored Matrix AI budgets are deferred; the owner funds the source. Pin requesting actor, executing owner, account/access-source/model, scope/worktree, Chat audience, authorizing policy and original payer on every run. Source exhaustion/disconnection pauses work and preserves the request; no fallback card or account. Usage is provider-reported or explicitly unknown. A queued or running shared run may be cancelled only by the member who requested it or by the project owner; other Contributors and Viewers see the cancel control disabled, and the audit records which of the two actors cancelled.

Canonical shared history is separate from the owner's private provider session: create a project/Chat-scoped session seeded only from shared authorized context. A changed account, root or audience requires a fresh session unless a tested adapter proves safe continuation. Serialize each shared Chat's queue; independent Chats in the project run concurrently subject to the same owner-source limits.

Multi-participant accounts, named actor seats on another member's host and automatic source routing are future scope, not first-release gates. Stable run binding fields preserve that extension point without implementing it now.

## Owner-controlled Git identity
Use the project owner's configured Git author/committer identity for newly created host commits and the owner's authorized forge credential for pushes and PR creation. Preserve existing imported authorship; never impersonate a collaborator or invent a configured identity. If the owner uses an explicitly configured service identity, show it as such. Missing Git/forge configuration is an owner setup action; collaborators never need to connect GitHub just to join.

In V1 no owner approval is required: a member with the Contributor preset commits, pushes and opens or updates PRs through the host's Git broker, and the broker executes them with the owner's identity and credential. The Matrix audit preserves the requesting human, AI run, commit SHA and remote PR URL independently of Git authorship; no automatic co-author trailers. Force pushes, branch-protection bypass and remote changes are not offered; branch protection on `main` is the forge's, configured by the owner. Per-operation owner approval bound to an exact tree/ref (the previous design) is deferred and can be reintroduced as a project policy without changing the broker.

Git/forge credentials stay in the local operation broker, outside Chat agents and PTYs: agents and sandboxed processes invoke broker operations and never receive the token, credential helper or alternate Git config. An org admin is not automatically a project's Git owner.

## Chats, worktrees and project concurrency
The default project group Chat uses the project's existing execution root. Sharing a project and joining it never create a worktree, a copy or a second writable root; a collaborator works in the same project on the owner's computer, one run at a time per Chat. Per-Chat worktree pickers, durable writer leases, parallel roots and shared-Chat worktree UI are deferred (S10) because they are a project-management concern that exists independently of collaboration.

Because canonical Chat already models project and worktree execution roots, a project may contain Chats whose roots are separate worktrees today. The share confirmation must inventory them visibly: every Chat in the project with its execution root, branch and dirty state, so that nothing is silently left out of the share and the owner sees exactly which roots collaborators will reach. A Chat whose root cannot be resolved blocks the share with an actionable explanation rather than being omitted. Chat deletion does not delete a dirty worktree, and missing roots and an offline home show recoverable states.

Every shared run executes in the OS-enforced isolation that the shipped scope-runtime already provides. Shared runs are transient scope-runtime units rather than gateway children, but the gateway holds the queue and output stream, and host-bundle updates stop the gateway and the scope runtime together. When the home loses track of a run for any reason (update, reboot, crash or partition), the executing run is marked interrupted in the timeline with the requesting member attributed, and only that member resubmits it; queued requests are preserved and start automatically once the home is back, each re-admitted only if its requester's membership evidence is still fresh. Reattaching to a run unit that survived the gateway is deferred. A Git worktree is not a security sandbox. Filtered workspaces, publication brokers and Chat audience data ceilings belong to granular sharing and are deferred with it; in V1 the whole project is the audience for every Chat in it.

## Integrations and ready-to-work sharing
A shared project declares required apps and the owner's configured source. Before acceptance and before the first run the recipient sees a readiness summary: ready, owner setup needed (missing Git identity, forge credential or AI source), host offline, or unsupported. The share preview names the source kind, the owner Git identity that commits will carry and the inventoried Chats and roots.

Shared runs use the owner's existing integration connections exactly as the owner's own runs do, on the owner's computer, with credentials that never leave the host. There is no per-collaborator connection grant, local credential broker, upstream scope narrowing or per-action approval in V1; those are deferred. Accepted risk, recorded as a product decision: a member who prompts the owner's agent can cause it to act through the owner's connections (for example send a message through the owner's Slack). Vendor-hosted connectors remain named external processors.

Run capabilities still constrain subprocesses, files, network and terminals through the sandbox. Direct terminal access grants explicit sandbox execution authority.

## Membership lifecycle

Membership invitations, acceptance, removal and roles use Clerk's own flow and dashboard. Departure immediately revokes org access; personal data remains personal and no grant outlives membership. Existing personal computers stay personal.

Deferred from V1 (retained below for the later administration release): invitation cost quotes and compute choices, sponsorship and payer changes, member-assigned computers, org-controlled recovery, and computer-to-computer transfer of projects/apps/Chats/files/worktrees. Nothing in V1 charges an organization or provisions a computer.

## Acceptance and exclusions

Release tests must prove the organization-only precondition on every path with no environment flag or cohort record consulted, fail-closed behavior on missing configuration, two-computer access through the relay with no platform authorization decision and no payload parsed or logged there, home rejection of forged/expired tickets delivered by the relay, revocation during partitions, multiple members using one owner source, default group Chat, member commit/push/PR through the broker under the owner identity with the requesting member audited, shared Codex and Claude runs on the project root, share-time inventory of every Chat root, sandbox escape denial, standalone shares of each resource type with only the Viewer and Contributor presets, organization-wide shares that stay pending until each member opens them, cancellation allowed only to the requester and the project owner, interrupted-run and preserved-queue recovery after the home loses a run, and Web Canvas / Web Desktop / Electron Desktop parity. Invite quotes, member-computer migration and managed Matrix group text are deferred and not release gates. Use real Postgres races and disposable enrolled VPSes; no claimed provider support without versioned live evidence. Include all applicable surfaces and a separate documentation PR in `FinnaAI/matrix-os-site/content/docs/`.

Deferred: granular folder/app/command/integration restrictions and Chat audience ceilings, per-operation owner Git approval, per-Chat worktrees and writer leases, integration delegation and local credential broker, Native Mobile and CLI parity for the new states, organization administration UI, groups, guests, invitation quotes and compute choices, sponsorship and org-sponsored AI budgets, member-assigned computers, computer-to-computer transfer, managed Matrix group text, direct client-to-home transport (per-home hostname and browser-trusted certificate), sharing between individuals outside an organization, participant AI accounts/source routing, copy-and-continue, pooled org computer, automatic whole-personal-machine adoption, arbitrary disconnected/offline writes, peer replicas as co-authorities, CRDT editor collaboration, general NAT/mesh/relay services, direct native Matrix room participation. Unsupported personal subscription modes must remain explicit unavailable states; sponsored API modes and both required harnesses still need acceptance evidence.

## Future: copy and continue on my computer

This is an explicit independent fork, not live collaboration or an ownership transfer. An authorized org member with copy/export rights can later choose a source revision/worktree and a destination computer. Pin the commit SHA; for dirty current state, offer an explicit owner-reviewed snapshot/patch including permitted untracked files. Git clone/bundle fetch of the pinned state is preferred, with Git LFS/submodules handled explicitly. Do not quietly omit dirty edits or claim a clean HEAD equals the current workspace.

Create a new project identity, private/default destination grants and a provenance link. The destination member uses their own Git identity, remotes and AI source. Do not copy credentials, integrations, provider resume state, private Chat drafts, grant lists or billing sponsorship. Chat history and app database state are separate explicit exports; Git alone does not clone them. Full repository export requires permission to its history; restricted-folder members cannot receive the entire Git object graph and need a filtered export. Existing collaboration on the source continues unchanged; later PRs are normal Git contributions, not automatic bidirectional sync. No clone endpoint or execution task is activated in V1.
