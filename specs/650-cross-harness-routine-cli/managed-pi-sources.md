# Managed Matrix Pi ordinary Chat routine source

Task6c is the `matrix_pi` managed Chat route, distinct from native `pi` Task6b and Terminal Task7. The managed origin has no Bot task or Bot ID. Scheduled execution still belongs exclusively to canonical Matrix Bot.

The actual managed runtime captures the admitted personal owner, Computer (from trusted routine runtime configuration), private Chat, turn/run, effective policy and immutable registered worker handle/generation before exposing worker tools. `createManagedPiAdmission` creates the `managed_chat` runtime under the existing managed Pi profile with `network: broker_only`. Startup adds `routine.cli` only when the existing routine runtime and fixed CLI transport are both configured. The actual registry inference signal binds the source to that worker incarnation; restored labels, model IDs, native Pi PIDs and caller IDs provide no authority.

The existing pinned Pi worker loop consumes an `AgentTool` called `matrix_routines`, selected by its explicit capability. Its parameters reuse the authoritative strict `RoutineCliOperationSchema`. This is an addition to the existing typed worker broker, not an MCP execution service. Recipe declarations and non-managed registry bindings reject this managed-only capability. Canonical Bot's direct `routine.propose`/`routine.control` tools and all native harness catalogs keep their existing routes.

Only strict routine intent crosses the Unix worker broker. The host resolves the exact currently registered binding and active run; no owner, Computer, Chat, Bot, task, source, executable, argv, environment, endpoint or accepted-phase override is accepted. The host invokes the actual published `matrix.mjs routines` CLI with fixed arguments, private IPC and the existing capability-only HTTP consumer/controller. Sources and receipts are minted by those real services. There is no owner-token proxy or public registration endpoint.

`registerManagedChat` checks the retained binding against the actual runtime registry and its original private inference signal. The shared producer validates the owner/private Chat, exact run/turn, `matrix_pi` driver, instance/selection, permission/interaction modes and live DB status at issue, consume and claim. Its source identity is `chat_run`, harness `pi`, route `managed`, with a fresh managed generation. No `BotRuntimeBinding` cast or fabricated origin task is used. Metadata reads create no target task; proposals acquire real canonical target tasks through the existing shared core.

Unknown human provenance retains the exact owner decision even in full access. Supervised file permission does not approve a remote routine mutation. Review/plan/shared/org/unsupported ceilings stay enforced. Routine activation, background model consent and integration permissions remain separate. Existing supervised/full-access artifact and integration capability filtering is unchanged.

The actual typed broker callback admits each call once. New `routine.cli` broker frames require `transport: "live"`; the strict broker schema rejects missing framing and this marker on every other capability. The client sends one newline-terminated frame while retaining its write direction. The socket server dispatches a valid live frame at that newline, then synchronously aborts its transport signal on EOF. This makes a transport-only abort observable during owner/CLI waits. Truncated, duplicate and trailing frames fail closed; the existing frame/connection caps, timeouts and shutdown drain remain. Existing non-routine control frames retain EOF dispatch, and inference streaming retains its existing newline behavior. The marker grants no authority: the registered binding and source/controller still decide every operation.

The worker projector's terminal tool event or independently observed live broker transport disconnect retires unconsumed call authority; cancellation begins actual unused-token revocation independently of CLI/worker drainage. Terminal tombstones cannot reopen. The tool callback's normal return does not end its parent run. Consumed committed receipts may still claim their real target while the parent remains live. Only the existing consumed-capability/receipt/digest validator reconstructs the internal `accepted:true` hint; it is neither public input nor stored invocation metadata. Parent end before claim denies the handoff; after canonical claim the target intent is independent.

The source closes before asynchronous worker/revocation cleanup. Cancellation ACK and drain timeout do not prove physical termination. Mutation uncertainty retains the original business UUID; no mutation retry or fallback target is introduced.
