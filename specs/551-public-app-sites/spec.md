## Goal and accepted scope
Publish owner-built Matrix apps at https://matrix.page/<random-id> with an optional globally unique friendly path. The owner purchased matrix.page during implementation and selected it as the shared-site domain. Anonymous visitors run the app and submit declared forms; owners manage submissions inside Matrix. Publishing is deployment, independent of marketplace listings. Customer domains and arbitrary Node/SSR backend deployment are deferred. V1 supports production Vite bundles and explicit public data/form capabilities.

The domain homepage (`/`, GET or HEAD) redirects with 302 to `https://matrix-os.com`, discarding the incoming query string. It needs no publication configuration and never redirects app, asset, frame or form paths.

The launch guide is an ordinary information app with guidance, support links, posts/channels and optional discount codes. Forms and the `publishing` manifest declaration are optional; existing eligible React/Vite apps publish their checked production output. Outbound HTTP(S) links open a separate tab with no opener/referrer, including links to other published Matrix apps. In-page anchors stay in the current frame. Both iframe and CSP allow popups while retaining an opaque origin and no private bridge/storage access; normal browser popup blocking still applies, and the anchor helper is not a global navigation allowlist.

## Requirements
R1: Permanent cryptographically random publication ID; optional atomically claimed lowercase slug; aliases resolve the same site. IDs are public identifiers, not authentication. Reserved routes cannot be claimed. Renaming never changes the ID; released aliases cannot be taken over unexpectedly.
R2: Owner publish, preview, update, change metadata/slug, version history, rollback and unpublish. Preserve the previous live version on any failed upload/build. Re-read the bounded regular-file manifest after building and after artifact collection; reject changed public/build settings or replaced app directories before upload. Serialise writes or use a revision predicate. Before a transaction, admit at most one publish per owner and four per process; hold admission through failed-candidate cleanup. Revalidate the exact authenticated owner/machine/handle/runtime slot/token epoch under owner admission lock before any deployment or management write, rejecting recovered, disabled, delegated or deleted runtimes. One logical site per owner/runtime/app, idempotent server-side.
R3: Upload only checked production output and approved public assets/config. Never publish source, environment files, build logs, database dumps, private app data or Matrix credentials. Refuse symlink/traversal paths, bounded files and bundles. Use immutable per-version asset keys.
R4: Owner-controlled Postgres holds visitor submissions; platform Postgres holds routing and deployment metadata, private dedicated R2 holds asset bytes. Only explicit publishing.data is exposed. Neither client-provided owner IDs nor app-auth cookies establish publication ownership.
R5: Manifest publishing configuration declares named forms with bounded per-field schemas. Public runtime exposes MatrixOS.site.data and MatrixOS.site.submit(formId, fields); never the private db/service/AI bridge. Anonymous submit validates exact fields server-side, caps body/rate/quota, uses idempotency keys, returns a coarse acknowledgement and reveals no other submission. No arbitrary SQL, table names, user-controlled upstream URLs or integrations are accepted.
R6: App code is sandboxed in a full-page iframe with no same-origin permission; server CSP enforces sandbox on every raw app HTML response, including direct navigation. Public top-level page is trusted Matrix-owned code. Parent verifies message source and fixed operation names. No shared-origin app storage, shell cookies, service workers, owner tokens or private API calls. Public assets permit bounded null-origin CORS without credentials for module scripts.
R7: Unpublish disables ID, aliases, frame/assets and public forms; stale versions cannot bypass the publication check. Do not cache active/revocation decisions; immutable bytes may be cached only behind fresh active checks. In-flight submission versus revoke has an explicit concurrency boundary. Rollback never rolls back or deletes submissions.
R8: Websites remain available when owner VPS is offline; form submission returns a safe unavailable response until the backend is online. V1 does not queue submissions or promise offline durable writes. Submissions persist through deployments and owner restart, are paginated, exportable and deletable by owner. Publication IDs, aliases and versions survive VPS recovery; submission data follows the owner database’s existing backup/recovery guarantees. List and export share an opaque keyset cursor using exact database timestamps and IDs, so concurrent insertion/deletion cannot shift existing page boundaries. Cached export bytes clear on page invalidation and confirmed deletion; late exports cannot recreate them.
R9: Shared owner feature controls provide equivalent behavior for Web Canvas, Web Desktop, Electron Desktop and Web Mobile where app management exists. Surface adapters may add chrome only. Native Mobile inclusion is conditional on existing app-management support and must be documented truthfully.
R10: Responsive anonymous launch/event acceptance: build app, publish, customise alias, visitor sees content, submits RSVP, owner reads exact saved record; update/rollback/unpublish, private data isolation and cross-site isolation verified. Public docs in separate FinnaAI/matrix-os-site PR under content/docs/.

V1 limitations: production React/Vite bundles only; at most 50 retained deployments per app (further updates fail safely until a retention upgrade); submissions export one bounded page at a time. Scoped Chat runs currently have integration-only tokens and cannot execute owner publishing actions; use Publish app or a genuine verified owner REST client. Scoped agent publishing is tracked in [ENG-233](https://linear.app/matrix-os/issue/ENG-233/featsites-allow-scoped-chat-runs-to-manage-public-apps). Native Mobile currently has preview-only app support and no owner publishing controls. The existing authenticated app window is the preview; the deployment dialog reviews public capabilities rather than hosting an anonymous draft. Customer domains, arbitrary server processes, offline form queues and hosted public draft previews remain deferred.

## Architecture and runtime wiring
Owner UI -> authenticated gateway app-site API -> machine-authenticated platform site management -> platform Postgres + dedicated private R2. Platform derives owner and runtime from its machine registry and validates machine bearer; customer-only publication, restricted preview machines fail closed. Public Worker on matrix.page forwards only supported public paths/methods to operator-configured platform origin, strips all cookies/authorization/forwarded identity, sets a dedicated edge proof and bounded timeouts. Platform requires a configured edge secret of at least 32 nonblank characters and validates the edge proof before any public read or submission; missing configuration returns unavailable. Platform resolves active ID/alias and serves trusted wrapper, sandboxed frame and checked assets. Public submit is routed to the registered owner gateway with a scoped signed service request; gateway checks the signed site/app/version/form configuration and stores in owner Postgres. Owner APIs never accept anonymous access. Existing large composition files receive module-registration wiring only; new behavior lives in focused modules under 500 LOC.

## Limits and failure handling
Zod 4 validates all route/query/body parameters. Every mutation has Hono bodyLimit. API calls time out in 10s, deployment uploads have a shared 25s deadline followed by bounded candidate cleanup, and asset transfers time out in 30s; redirects rejected. Upstreams come only from operator-controlled registry/config. Bounded streamed reads, file counts and bundle sizes. Anonymous reads share 16 admission slots held through body consumption/cancellation or a 30s transfer deadline, with 1,200 reads per verified source and 12,000 globally per minute before DB/storage admission. Any in-memory collection has cap/eviction; DB pools close only through resource owner. Optional visitor schema setup uses a separate owned one-connection pool with 5s acquisition/server statement limits, 2s DDL lock limit and 7.5s client read limit that discards stalled sockets. Setup failure leaves visitor storage unavailable while information-only publishing continues; shared owner queries retain their existing behavior. Generic public/client errors, server-side coarse logging. Multi-write DB flows are transactional; immutable upload plus activation cannot be one distributed transaction: upload before activation and delete candidates only when the transaction callback did not finish. A rejected commit acknowledgement has an ambiguous outcome: preserve uploaded bytes until an authoritative reconciliation or owner erasure; never delete a potentially activated version. Owner-prefixed dedicated assets make aborted uploads discoverable for account erasure. No activation on missing storage configuration.

Unpublish concurrency boundary: the platform locks the publication row through form admission and forwarding. New requests after revocation fail. A request admitted beforehand may still persist if the forwarding transport times out and the gateway transaction subsequently completes; distributed cancellation is not promised. Gateway database lock and statement timeouts bound that work. Account deletion admission precedes publication locks, blocks new publication work and immediately closes public access; erasure removes registry/configuration and the owner's dedicated asset prefix.
