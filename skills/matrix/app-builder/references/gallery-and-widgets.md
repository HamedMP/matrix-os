# Gallery-ready apps and desktop widgets

Use the user's reference images to choose a deliberate subject-specific visual direction. Travel, receipts, writing, weather and a focus timer should have different information architecture; repeating one sidebar/dashboard with new colors is not a design system. Keep coherent common navigation, focus, states and permissions. Create a short app DESIGN.md and verify the primary flow before secondary screens.

Discovery is **Matrix App Gallery**; installed applications are **Apps**; integration discovery is **Tools**; a copyable blueprint is a **Template**. Do not use App Store or AppGallery for the Matrix discovery surface. A public preview uses fictional or deliberately consented sanitized data and records the actual app version/viewport. Generated icons/illustrations are artwork, not screenshots. Never fabricate ratings, installs, creators or available integrations.

Mobile is a primary app layout. Compose for narrow container width, safe areas, touch, keyboard, low bandwidth, error and loading state. Keep important data/actions visible at 360–390px; use purposeful local scrolling for dense tables. A desktop screenshot scaled down is not a mobile preview. Run the production build and verify through each available surface, including persistence after reopening. Native Mobile qualification uses the Expo dev client, not Expo Go.

Check the current runtime before choosing an API. Web Desktop's sandboxed app bridge and Native Mobile's authenticated WebView are different paths; a missing native bridge is an implementation gap to resolve, not a reason to declare the app desktop-only. Do not claim native save/reopen or offline writes based on responsive CSS. Keep last confirmed data visible during revalidation. Cache bounded owner/runtime/app-version-scoped snapshots, clear on account/runtime changes and permission revocation, and never cache auth/provider secrets. Pending offline edits require conflict handling and explicit synchronization state.

Widgets are a planned compact app presentation. Read specs/552-gallery-widgets-platform-images/spec.md when working in the repository. Current Matrix app manifests/OS-view schemas do not yet accept the proposed widget declarations. Do not invent window.MatrixOS.widgets or a universal window.MatrixOS.notify API. The future host uses shared scoped data/actions across Web Desktop, Electron Desktop and Web Canvas; mobile adapts layout while preserving actions. Build a proposed widget view alongside the real app, then wire and qualify the host contract before presenting it as installed.

Matrix already has a gateway scheduler and the manage_cron tool; use the current scheduler for reminders/refresh when it matches the task. Native notifications and Expo push exist for specific OS flows. General app notification delivery requires an app permission check, owner-scoped durable event and validated destination; do not have an app call Electron IPC or Expo push directly. Inspect the current gateway capabilities and finish available installation/registration paths before claiming the host cannot do an action. A capability is verified by actual runtime result, not by an assumed tool name.

For image artwork, prefer a configured platform-funded image service when available. It is enabled by platform policy and limited by an included allowance; keep provider keys off owner runtimes/apps. Explicit owner-key generation can remain an alternative. Never silently change funding source, consume another service's allowance or bypass disabled policy. Read the actual generate_image tool contract rather than assuming a model ID, endpoint or notification bridge.
