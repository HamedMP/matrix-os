# Mobile-first apps and responsive landing pages

Read [Expo loading and caching](expo-loading-and-cache.md) for the actual Native Mobile session/WebView path, safe asset/read/view caches, foreground revalidation and required cold/warm launch measurements. Responsive CSS alone does not verify native launch, persistence or cache behavior.

Web Mobile and Native Mobile are required for the primary flow. Start with the phone task, navigation and data states, then adapt the same information and actions to larger Matrix windows. Design for the actual app container width, not the device label: a narrow Electron Desktop or Web Canvas window also needs the compact composition. Record the observed viewport and container width; do not branch layout on user-agent strings. Keep the selected product style coherent across layouts.

## Compose for the space

- Use fluid grids, wrapping controls, flexible tracks such as `minmax(0, 1fr)`, and `min-width: 0` on shrinking flex/grid children. Give prose a readable maximum measure; use wide-window space for relevant content or a useful detail pane. Do not stretch controls or invent filler statistics.
- Let the primary task determine breakpoints. Stack forms and actions in reading order; keep the primary action reachable and drafts intact through resize, rotation and keyboard changes. A sidebar can become accessible compact navigation or a sheet. Avoid a fixed minimum width for the whole app, fixed-height clipping, and viewport-wide children inside smaller containers.
- Preserve every meaningful field, action and state. Do not hide fields to fit a screenshot. On phones, tables can become labeled record cards with an accessible detail view; charts need readable labels, a textual summary and tap/keyboard selection rather than hover-only tooltips. Detail panes can become full-width routes or sheets with visible close/Back controls. Use horizontal scrolling only for essential two-dimensional tables, timelines or boards: contain it in a labeled region, show overflow cues and provide keyboard access. Do not mask clipped content with body `overflow-x: hidden`.
- Compact navigation needs a labeled button, expanded state, usable links, visible keyboard focus and a reliable close action. Modal sheets manage focus, Escape, background inertness and return focus; hidden navigation leaves the tab order. Keep app-level Back predictable: detail → list → app root without losing filters or drafts. Verify native host Back and gesture behavior through the actual supported host contract; do not invent a `MatrixOS.back()` API. Warn before discarding unsaved edits. No hover-only actions or essential drag-only gestures.
- Touch hit areas must be at least 44×44px, with room between adjacent controls. Check long labels, large text, screen-reader names, focus order and error announcements. Respect inherited theme changes, contrast, reduced motion and supported accessibility settings.

## Phone viewport, safe areas and forms

Use the real host dimensions and documented insets. For web content, a viewport declaration can include `viewport-fit=cover`; use dynamic viewport sizing (`100dvh`, with an appropriate `100%`/`100vh` fallback) so browser chrome and the on-screen keyboard do not cover the primary flow. Avoid double-applying insets already consumed by native host chrome. In the app's own edge-to-edge content, use the applicable `env(safe-area-inset-top)` and `env(safe-area-inset-bottom)` together with normal spacing. Test actual scroll regions and sticky actions rather than assuming these CSS rules alone solve the keyboard.

Use labeled inputs and the appropriate `type`, `inputmode` and autocomplete. Keep input text readable without unwanted zoom; keyboard Next/Done, submit, validation, cancel and retry must work. The focused field, errors and save action stay reachable while the keyboard is open. Preserve drafts on keyboard dismissal, rotation, navigation and a failed save. Return focus deliberately when closing details. Never use a global scroll lock that traps form content behind the keyboard.

For landing pages, reflow headings, CTA groups, anchors and navigation. Use a stable imagery aspect ratio and an actual phone composition for mobile product previews, rather than shrinking a full desktop screenshot into unreadable text. Avoid fixed-height heroes and sticky elements that cover content.

## Verify the installed app, not just its screenshot

Inspect **360px, 390px, 600px, 820px, 1024px and 1440px** app-container widths, plus intermediate resizing. These are test widths, not mandatory CSS breakpoints. Record observed viewport and app container dimensions, since Matrix chrome changes the usable space.

Launch through Matrix in phone Web Mobile and the actual Native Mobile app using an authorized installed development client on a device or simulator. A desktop resize, standalone browser preview or mocked bridge is supplementary evidence, not proof of mobile runtime behavior. Also check Web Canvas, Web Desktop and Electron Desktop. Native app launch, authenticated bridge access, save/reopen, safe areas, on-screen keyboard and native Back require actual native-host evidence.

For a data app, perform a real owner-Postgres round trip on each required mobile surface: load → create/edit → await confirmed save → close/reopen → read the saved record. Cross-open the same record on another surface. Exercise a failed write without losing the draft and retry it; a successful toast or in-memory list update is not saved data. For tools without persisted records, verify their complete primary task and any state they claim to retain. Test populated/empty/loading/error/saving states, accessible navigation, essential scrolling, touch interactions, keyboard behavior, themes and reduced motion.

Discover the installed host's actual typed bridge capabilities before calling them. This guidance does not implement the Native Mobile launch/bridge work tracked separately. If launch, authentication, bridge, persistence or verification tooling is missing, repair or escalate the host dependency and record a developer check pending. Complete independent app work, but do not claim mobile readiness until those checks pass. Never substitute an in-memory save, copy credentials, weaken authentication/policy or add desktop-only/not-built-for-mobile product copy as a workaround. A missing capability belongs in the developer handoff, with the observed failure and required host repair; product error states remain truthful and retryable.

Record in BUILD-REPORT.md: surface and host version, observed widths/insets, actual primary actions, record/save/reopen result, keyboard/Back/accessibility checks, console/network errors, screenshot/recording paths and pass/fail/pending. Use fictional example data for shared screenshots. Never report a screenshot, build or skill change as proof that an untested host capability works.
