# Slack company transport

This module consumes a signature-verified owner-home bridge envelope. The platform owns Slack OAuth credentials, employee links, app/workspace installations, approved channel bindings, Slack signature verification, and the final Slack API publication boundary. The owner home stores company event receipts, exact thread-to-Chat mappings, canonical request references, bounded source proofs, and reply outbox state. No Slack token is stored here.

`SlackCompanyService.receive` validates fresh existing Project membership and exact owner/organization/channel binding, then commits the inbox before acknowledging. Direct messages and unbound company channels are rejected here; the separate personal Slack service handles DMs. Anonymous actors and Slack names never become execution identities. The source event timestamp must be within seven days and no more than five minutes in the future.

`createSlackThreadResolver` derives one stable canonical Chat per app/team/channel/thread and approved Project. It validates the Project execution root, uses `MATRIX_BOT_SELECTION`, binds the dedicated company recipe through the injected owner setup callback, and derives inherited collaboration authority through the existing Project inheritance resolver. It creates no child membership copies. A crash may leave an owner-private Chat before inheritance publication; replay resumes from the same deterministic identity. Current qualified Pi workload eligibility is supplied by startup, not fabricated in this module. Optional owner initialization uses the canonical shared queue to establish the real provider binding; it never invents a bound turn ID.

`drain()` admits requests through the existing `CollaborationChatExecutionAdapter`, which must use a canonical ChatRepository with its fresh shared authorizer installed. The existing canonical dispatcher executes Pi. This module starts no independent LLM loop. Project execution-root provenance must be resolved by the execution adapter and pinned to the canonical queued Turn/Run.

A retry retains the original request text, exact actor, deterministic client request ID and revision. If an admission conflicts, the exact canonical actor/request identity is queried before any revision is refreshed. An already accepted request is reconciled rather than resubmitted with changed content. `createSlackCanonicalReaders` derives requester identity, run state and committed assistant text from the exact canonical queue/run; pending approvals and input requests stay pending.

Optional thread context fetch happens after durable acknowledgement, reads only the receipt-bound thread through the platform broker, and includes at most 20 messages and 16 KiB of quoted source material. Failure preserves the original mention and adds an honest unavailable marker. Provider pagination limits and local message/text/byte truncation mark both the prompt and captured Brain evidence as partial. Only explicitly approved company channel bindings can automatically capture the mention and bounded thread evidence into the Project Brain. Full channel-history, email and calendar ingestion are later connectors.

Company Brain text remains untrusted. At most six source identities are checked together in one final live database snapshot after external authority and receipt callbacks settle. Source ID/incarnation/revision proofs are persisted with the prompt and revalidated before each canonical admission, including retries of pinned text. Legacy revision-only proofs fail closed. Before output, fresh Project and child Chat authority, canonical actor/run identity, and source incarnation/revision/deletion checks must all pass. The platform performs another exact receipt-bound channel/thread/installation-generation authorization before sending. Its signed publish_reply callback calls authorizePublication with organization, actor, Project scope, app/team/event identity and the SHA256 of raw UTF-8 reply text. The home derives its own completed inbox and sending outbox, checks the live lease and exact canonical result, reauthorizes the Project/Chat and verifies source incarnations/revisions after metadata lookup. Caller-supplied source proofs are rejected. Outbox text remains plain; the platform performs Slack markup escaping once.

Inbox: at most 1,000 active and 10,000 retained events per owner; bounded admission batches of 10; eight retries with exponential backoff; 60-second leases. Results reconcile in bounded batches of 20; pending and temporarily unavailable results advance their check timestamps so later completed requests can progress. Reply outbox: three known-safe retries; 30-second delivery leases. A crashed/ambiguous send becomes `uncertain` and is never automatically resent. Events older than 24 hours are retired from processing; terminal receipts expire after seven days; inactive mappings expire after 30 days. Cleanup recurs through startup's drain timer. `close()` stops new admissions and waits for its active bounded drain; the gateway pool owner closes the DB.

An optional receipt-bound progress reaction runs only after canonical admission; its failure does not lose accepted work.

No interactive approval or stop UI is added here. Users can inspect/control canonical shared Chat requests through existing collaboration controls. A Slack-native approval flow, history backfill, organization-owned hosting, Brain app, and rich channel status UI remain separate work.
