# Google-copy lineage and purge foundation

ENG-355. This module adds no endpoint, runtime hook, timer, provider client or deletion adapter.
It uses an injected Kysely/PostgreSQL database; the host owns migration ordering, scheduling and pool shutdown.

- `record`: trusted server composition registers owner, exact connection **generation**, entity kind, opaque reference, SHA-256 content hash, every source binding and explicit owner retention choice. Retention is positive and at most 30 days. Existing origins are append-only; mixed copies inherit the earliest deadline. Content changes require the exact previous revision. Register before exposing a copy; registration does not intercept or retroactively discover files.
- `inspect`: exact-owner lineage projection. Metadata contains no raw Gmail content, filesystem path, credential or provider response.
- `assertReadable`: provenance prerequisite only. The caller supplies bindings obtained from the current server-side processing authority. Do not expose those inputs as a client self-approval API. Revalidate the authority and exact saved-copy revision after awaits and immediately before context assembly, release or dispatch.
- `requestPurge`: exact owner/account tombstone plus idempotent receipt. All managed mixed-origin entities mentioning that account are scheduled as whole copies. Different request keys for one account reuse one receipt, while every key remains bound to its original account. A tombstone never silently expires. Renewed consent must use an explicit, newly authorized connection generation; the module provides no tombstone-clear shortcut.
- `claimPurge` / `executeClaim`: bounded leases, revision-conditional settlement, bounded retries and durable unresolved states. Concurrent workers cannot attest the same claim. Trusted kind handlers must atomically compare owner and expected hash before deleting, be idempotent after crash and respect cancellation. Missing handlers, modified copies, invalid outcomes and timeouts never attest deletion. A timed-out adapter could still finish a side effect; only a subsequent live lease may verify and report its result.
- `status`: exact-owner receipt with `coverage: registered-copies-only`. Completion attests only the registered managed copies included in that receipt. It does not attest provider, cache, backup, historical or unregistered-copy deletion. Disconnect is independent.
- `queueExpired(batch=100)` and `cleanupDeleted(batch=100)`: host calls repeatedly on a bounded schedule, draining work before pool shutdown. Expired copies are unreadable before scheduling. Completed entity/hash/lineage metadata is pruned after 30 days, preserving count-only receipts and account-generation tombstones. Active and unresolved records are never evicted to satisfy a cap.

Defaults: 200,000 registry entities, 10,000 per owner, 20,000 deletion jobs and 20,000 idempotency keys/requests, 32 origins per copy, five attempts, 60-second retry interval, 30-second maximum handler execution. Cap exhaustion fails closed. Tombstones and idempotency metadata remain bounded and require an explicit owner-account lifecycle policy in host composition; they cannot be silently removed while they prevent stale writes.

Source provenance must be inherited when deriving/importing/copying content. Actual transcript, saved context, attachment, cache and processor adapters, owner authentication, profile authority, recurring scheduling and production qualification belong to host integration. This foundation does not establish those controls on its own.
